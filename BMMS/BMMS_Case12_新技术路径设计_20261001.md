# Case12 新技术路径：N 优先分核、B 全 K 驻留、首块边加载边计算

日期：2026-10-01。设计基线：`BMMS_V12/v12_baseline_r41.asc`。

**建议停止在原 r30 分工上继续调 K1、预打包 B 或微调 merge。下一版改成：将 128×128 计算块按 N 优先展开，连续分配给各核；同一核连续计算同一个 N 面板上的多个 M 块，B 在 L1 中保留完整 K，并在首个 M 块计算时逐段填入。**

这次改变的是任务归属与输入复用周期。旧 r45 已经有 B 驻留、N 外循环和双 L0C，不能把这些单独称为新方案；本设计的关键是让连续多个 M 块真正落到同一核，并同时控制分核不均衡。

本文件是可实施设计及 CPU 模型审计，**尚未生成新 `.asc`，尚未执行新路线的 CANN 编译、NPU 精度或性能测试**。r41 不变。计划中的下一性能实验编号为 `v12_r59`，不代表已交付 r59 提交文件。r58 诊断文件保留，但其结果不作为本路线启动的前置条件。

## 1. 当前路径的问题究竟在哪里

15 点均 Pass，现有证据没有指向数学语义错误。“路径有问题”目前应理解为任务划分、数据重读与流水组织存在改进空间，而不是已证明计算算法不正确。

结合用户上一份文档以及实际 host planner 的已有枚举：

|信息|当前可采用的结论|
|---|---|
|输入|B=1，K=1536，TB=false|
|范围|1280≤M<1536；4096≤N<6144；M 按16对齐，N按64对齐|
|TA|仍未知；TA=true 时还要求 M%64=0|
|原路由|r30 producer，AM128、BN256、K1=256、K0=64|
|原分核|pN=2，pM=mTiles，tasks=blocks=cores|
|与全部证据兼容的核数|20、22、24；本地20核不能直接证明 Judge 也传20|
|20核条件下|M=1280，pM=10，pN=2，每任务只有一个 M 宏块|

### 1.1 原分工不能获得核内跨 M 的 B 复用

原路径中，多个 M 分片各自读取同一份 B。已知 Case12 计划每核只有一个 M 宏块，因此把原循环简单改为 `for N / for M`，M 循环仍只有一次。

旧 r45 在这种计划上把 BN 从256降到128，却没有让第二个 M 块归同一核：B 全 K 驻留的核心收益没有兑现，A 重读和小块开销却增加了。r45 的其他合成形状可能有跨 M 复用，不能把上述结论泛化到旧测试的所有输入。

### 1.2 “对 B_LOAD_X2 敏感”不等于“预打包 B 会更快”

上一份文档中，增加 A/B/ring 加载分别带来约21.91/32.99/4.72μs增量。这支持继续调查输入搬运，但不是可直接相加、扣除的时间分解。原宏块 B 请求字节本来就是 A 的两倍，不能仅凭绝对增量认定 B 每字节效率更差。

r56/r57 只是改变 B 的全局布局，**没有减少多个 M 分片各自读取 B 的次数**，还增加了打包、GM写读和同步。两版初筛中位耗时分别增加6.83%和9.62%，因此不继续沿用这个方案。

### 1.3 单波不等于流水满载，原 flat tie 也不否定新分工

`tasks=cores` 只证明逻辑任务数覆盖核组，不能证明 MTE/MMAD 没有等待。r41 的原展平指标针对128×256宏块和原 producer；本方案改变了块宽、遍历顺序与驻留对象，不应继续用旧 `flatPeak < oldPeak` 作为新方案是否值得尝试的判据。

## 2. 为什么不直接固定 pM=1 或 pM=2

先枚举了 pM=1/2/4、N 分片粒度16/64/128，再与原计划比较。固定二维网格仍会遇到量化不均衡。

例如20核、M1280、N4096：

|分配|总 A+B 请求|最重核有效计算单元相对原版|问题|
|---|---:|---:|---|
|原10×2，128×256|180MiB|1.000×|B重复加载10份|
|1×20，N按128分片|132MiB|1.250×|省字节，但计算长尾增加25%|
|2×10，N按16分片|174MiB|1.016×|细分片带来的额外 A 加载吞掉多数收益|
|本方案：N 优先连续块分核|138MiB|1.000×|兼顾复用与工作量均衡|

在全部20核候选中，固定1×20、N按128分片时，最重核计算量最差可增加42.9%。因此不把某一个 pM/pN 常量作为新主路径。

## 3. 新任务划分：按 N 优先连续分配计算块

定义：

```text
AM = 128
BN = 128
mTiles = ceil(M / 128)
nTiles = ceil(N / 128)
T = mTiles * nTiles

核组 g 的范围：
begin = floor(g * T / cores)
end   = floor((g + 1) * T / cores)

对 flatId：
nTile = flatId / mTiles
mTile = flatId % mTiles
```

这里 M 索引变化最快。每个核的连续区间由若干段组成，一段内 `nTile` 不变，M 连续。每进入新的一段，只装载一次该段所需的完整 K×128 B 面板，供该段内所有 M 块使用。

```text
全局块序列：
N0: M0 M1 ... M9 | N1: M0 M1 ... M9 | N2: ...

20核、M1280、N4096：总共320块，每核16块。
某核可持有 N0 的10个 M块 + N1 的6个 M块。
另一个核从 N1 的剩余 M块继续。
```

核边界可能切开一个 B 面板，此时相邻核各加载一份该面板。**允许这种有限重复，不追求 B 全局只读取一次。** 强迫面板完整归一个核，会重新引入严重负载不均衡。

同一核进入一个 B 面板段后，只保留当前 C 宏块的累加状态，不需要同时保留该段所有 M 的 C。每个 C 仍完整累加1536个 K，再交给 AIV 做 max。

### 3.1 数学语义与覆盖

接口沿用当前比赛 C ABI，输入 dtype=1/2 对应 FP16/BF16，两种 TA，TB=false；输出每个 batch 一个 FP32 标量。本专用路径仅处理 B=1：

```text
C[m,n] = sum_k op(A)[m,k] * B[k,n]
y[0]   = sum_m max_n C[m,n]
```

flatId 区间互不重叠且恰好覆盖 `[0,T)`，因此每个有效 C 元素计算一次。K不分核，不对部分 K 结果提前 max。最后只能先合并各核对同一行的最大值，再跨 M 求和；不能先对每核的局部行最大值求和后再合并。

## 4. L1 与 Cube 流水：首个 M 块边填 B 边计算

主配置：`AM128 / BN128 / K_A256 / K0=64`。

### 4.1 每个 B 面板段的流程

1. 首个 M 块：K 分六段，每段把 A 的128×256块加载到 A 双缓冲；同时把 B 的256×br片段写入完整 K 的最终 NZ 位置。该段 A/B 就绪后即可发起对应四次 K0=64 MMAD。
2. 六段完成时，完整 B 面板已经在 L1 中。该段后续 M 块仅加载 A，L0B直接从驻留 B 读取。
3. 同一段内，当前 M 的最后一个 K 阶段可预取下一 M 的第一个 A 阶段。
4. 切换 N 面板段前，确认旧 B 最后一次 L1→L0 读取结束，再覆盖 B。不可只凭“已经发起最后一次 MMAD”判定 B 可写。

与 r45 的区别是，主方案不先完整预载384KiB B再启动首块计算。保留“一次完整预载 B”的对照配置，仅用于区分启动延迟与 DMA 描述符成本：分段填充每个 B 面板有6条搬运，整面板预载只有1条，前者也不是必然更快。

### 4.2 B 的 NZ 地址与生命周期

对 TB=false，B 在 L1 采用完整 K 的 NZ 步长。以元素为单位：

```text
offset(k,nLocal) = floor(nLocal/16) * K * 16 + k * 16 + nLocal%16
```

首块第 kBase 段加载时，目标起点为 `kBase*16`；`nValue=256`、`dValue=br`、`srcDValue=N`、`dstNzC0Stride=K=1536`。不能把目的 NZ 步长误写成256，否则后续 M 块会读到错误布局。

L0B 读取仍用完整 K 的 stride；A 的 NZ布局按 TA 分支保留既有处理。CPU 已独立比较整面板 NZ 打包与六次增量填充，8种面板宽度、192个 K0切片均一致；这不是设备端 DMA 参数/异步行为的证明。

### 4.3 显式资源表

|位置|用途|字节|KiB|
|---|---|---:|---:|
|L1 B1|1536×128×2，全K驻留|393216|384|
|L1 A1|2×128×256×2，A双缓冲|131072|128|
|L1合计|主配置|524288|512|
|L0A|2×128×64×2|32768|32|
|L0B|2×64×128×2|32768|32|
|L0C|2×128×128×4|131072|128|

主配置恰好用完当前工程采用的512KiB L1预算，无额外 L1 空间。实现时查询设备容量、核对所有分配及对齐后编译验收，不把这张表当成所有设备型号的容量承诺。若不能满足，448KiB版本（A双缓冲K_A=128）作为资源兼容对照，不能把其结果与六段流水混为一谈。

两个 L0C 槽分别等待自己的 FIX_M 事件后复用，使下一块 MMAD 能与上一块 Fixpipe 重叠。这里沿用 r45 已实现过的槽级生命周期，不用一个全局 pending 标志把两槽又串行化。

地址约束遵守对应 API：例如 L0A/L0B 基址要求512B对齐，L1与UB有各自约束；不能把“512B访存优化粒度”一律解释成所有 GM 起点的合法性要求。参见 [Ascend C General Restrictions](https://www.hiascend.com/document/detail/en/canncommercial/800/apiref/ascendcopapi/atlasascendc_api_07_0004.html) 和 [官方 ND2NZ 参数说明](https://asc.gitcode.com/api/SIMD-API/%E5%9F%BA%E7%A1%80API/%E7%9F%A9%E9%98%B5%E8%AE%A1%E7%AE%97%EF%BC%88ISASI%EF%BC%89/%E7%9F%A9%E9%98%B5%E8%AE%A1%E7%AE%97%E7%9A%84%E6%90%AC%E5%85%A5/%E7%9F%A9%E9%98%B5%E6%95%B0%E6%8D%AE%E6%90%AC%E5%85%A5%E8%87%B3L1-Buffer/GMToL1%E9%9A%8F%E8%B7%AF%E8%BD%AC%E6%8D%A2-ND2NZ%E6%90%AC%E8%BF%90%EF%BC%88DataCopy%EF%BC%89.html)。实际实现以板上 CANN9.0 的头文件及 dav-2201 编译结果复核。

## 5. AIV 与末端归约要一起适配

### 5.1 Consumer

继续使用一 AIC 配两 AIV 的混合 kernel。每个 AIV 处理当前宏块的一半行，ring 的 READY/FREE 协议按既有版本保留，并验证两个 consumer 均完成读取后才能复用槽。

区别在于计算顺序改为 N 优先：每个 AIV 的 UB 要保留其负责行的整条 runningMax，而不是只保留当前64行。用 `M/2` 个 FP32；逐宏块映射到 `mBase/2` 的局部位置。尾块 `ar<128` 时，两个 AIV 各持有 `ar/2` 行，映射和输出地址均按实际 ar 计算。

run 初始为负无穷，N 尾部也为负无穷，禁止用零污染全负输入。所有块消费完后，各组写入 `partial[group][M]`。没有被本组计算覆盖的行保持负无穷；归约仍然正确，不依赖每核恰好覆盖全部 M。

### 5.2 Parallel merge

新方案 partial 从原 `2×M` 增长为 `cores×M`。不能继续直接让一个 AIV 顺序执行20次整行加载与 Max，再把增加的尾声误判为 B 驻留失效。

第一实现版本使用：

1. 所有 partial 写完、完成 MTE3 fence，第一次全局同步。
2. AIV 按32行条带分工，每条带加载全部核组的 partial，可用一条带 stride 的 DataCopyPad；沿核组方向做 Max，写 `mergedRows[M]` 的唯一对应区间。
3. 第二次全局同步后，只让一个 AIV读取完整 mergedRows，沿用原完整 M 的 ReduceSum。

首版不做“局部标量 sum 再相加”，以减少 FP32 求和树变化。Max 的分组对有限正常数值不改变数学结果，但 NaN、带符号零及设备具体行为仍遵守原算子契约；未经验证不扩展特例语义。

多了一次全局同步，这是真实成本。保留串行合并作为本地消融对照；若并行合并在新 partial 大小下不划算，以端到端实测选择。原 pN=2 时 merge 弱敏感，不能证明 pN=20 后仍然无关紧要。

### 5.3 UB 与 workspace

单个 AIV 首版显式预算：

|UB缓冲|大小|
|---|---:|
|C半宏块输入，单槽|64×128×4 = 32768B|
|runningMax|M/2×4，最大3040B|
|当前64行最大值|256B|
|merge条带|cores×32×4；按上限64核预留最多8192B|
|最终M向量与ReduceSum临时区|2×M×4，最大12160B|
|标量输出|32B|
|上述总计上限|56448B，分配还需逐项检查对齐|

workspace 各段分别对齐，算术使用64位：

```text
ring        = cores * 2 * 128 * 128 * sizeof(float)
partials    = cores * M * sizeof(float)
mergedRows  = M * sizeof(float)
```

20核、M1280时，ring=2.5MiB，partials=100KiB，mergedRows=5KiB。原 ring=5MiB、partial=10KiB。ring容量变小不等于总传输变少：有效 C 的 GM写入加回读仍约为 `8*M*N` 字节。

## 6. CPU 模型结果：有明显请求量空间，但不能等同加速

复用此前从 r41 实际 host planner 提取得到的640条兼容状态，比较矩形候选和本方案，共5440条候选记录。重新核对 r41 SHA256，且原计划 peak_cells 与归档一致。不是拿手写启发式代替真实基线。

### 6.1 20核、M1280、全部32个N候选

以下百分比覆盖两种 TA 的兼容记录；TA 不改变逻辑字节模型，不能据此假设两种布局时延相同。

|指标|新路线相对原版|
|---|---|
|A逻辑GM→L1字节|1.941～2.000倍|
|B逻辑GM→L1字节|0.100～0.155倍，即减少84.5%～90.0%|
|总A+B字节|减少22.5%～26.7%|
|最重核A+B字节|减少20.8%～27.3%|
|最重核有效 C 单元数|0.944～1.030倍，最多增加约3.03%|
|MMAD调用次数|1.941～2.000倍，但每次N宽减半，总有效算量不变|
|A+B ND2NZ调用数，分段填B版|增加10.0%～15.3%|
|有效C ring总写读量|不变|

部分具体例子，单位MiB：

|N|原A+B|新A|新B|新A+B|新最重核计算量/原版|
|---:|---:|---:|---:|---:|---:|
|4096|180.000|120.000|18.000|138.000|1.000|
|4160|185.625|123.750|18.938|142.688|1.030|
|5120|225.000|150.000|15.000|165.000|1.000|
|6080|268.125|180.000|23.812|203.812|1.000|

22/24核兼容状态也全部完成结构枚举；最重核有效计算量的最大比值分别约1.030、1.023。它们是CPU模型，不是当前20核设备对22/24核的实测。

### 6.2 必须正视的失败风险

- 原B跨核请求可能已被L2部分吸收。逻辑请求减少不保证 HBM流量或端到端时延等比例减少。
- B完整K的L1布局 stride=1536 与旧256不同，可能产生新的 MTE1/bank 冲突或加载效率问题。r45 的失败提醒我们不能只看 GM 字节。
- BN减半让MMAD、Fixpipe、ring握手接近翻倍；有效FLOPs不变不代表指令开销不变。
- A重读接近翻倍、DMA调用更多，可能抵消B请求减少。
- L1无余量，面板切换、初始填充、跨宏块预取与L0C双槽之间的事件必须正确；不能靠过多全流水屏障“修好”后忽略性能损失。
- 新partial与额外同步可能拉长尾声。

因此不能根据“B减少85%”宣称能下降30μs，也不能承诺达到榜单参考85～89μs。**这条路径值得实现的依据，是同时改善总请求和最重核请求，并控制住计算长尾；性能结论还必须实测。**

## 7. Host/API 实施草图

建议新增专用模块，不修改原 r30 或覆盖 r41 文件。独立 plan 不再复用有 pM/pN 语义的旧 Plan：

```cpp
struct Case12Plan {
    int32_t M, N, K;               // K=1536
    int32_t mTiles, nTiles, blocks;
    int32_t totalTiles;
    uint64_t ringOffset, partialOffset, mergedOffset;
};
```

入口先限定已知可验证域：B1、K1536、TB=false、两种16位dtype、M/N范围及既有pitch条件；保留当前实际路由优先级，Case11等仍由原路径处理。新路线运行时从真实shape计算plan，不依赖 case编号、输入数值或跨调用缓存。

第一版不要新增 `N%128==64` 这种未被当前证据确认的门槛，同时覆盖N%128=0和64。也不要要求新分块整除M或N；必须实际实现尾块。资源或合法性检查不成立时回到r41。

```text
Producer(group):
  [first,last) = 连续 flatId 区间
  按相同 nTile 把区间切成 runs
  for run:
    等待旧 B 的最后一个 L1 reader 释放（首段除外）
    for mTile in run:
      获取独立 L0C 槽
      for kStage in 0..5:
        双缓冲加载 A
        若是本 run 第一个 M：同时向最终 B NZ 位置填当前 K 段
        等待本段 operand READY
        四次 K0=64：L1→L0，MMAD FP32，按原K次序
      Fixpipe 完整K结果到 ring；发布 READY
  排空已发出的设备操作

Consumer(group,sub):
  runningMax[:] = -inf
  按同一 flatId 顺序消费 ring
  更新每个有效 M 行的局部最大值
  写 partial[group][M]
  完成写入 -> 同步 -> 并行跨组 Max -> 同步 -> 原完整M ReduceSum
```

真实实现必须单独定义 A槽、L0槽、C槽和B面板段的所有权。特别是跨 run 的 A 预取不能顺便覆盖尚在使用的B；ring槽可复用与L0C槽可复用也是两个不同事件。

## 8. 最小实验顺序与停止条件

不增加隐藏shape探针。先利用已知完整范围和本地卡，验证新机制。

### 步骤A：只建立一个完整新模块

计划 `v12_r59`：N优先连续块分核、B驻留、K_A256、首M分段填B、双L0C、适配后的rowmax与合并。FP16/BF16各两种TA，总计4种新kernel特化；现有fallback保持。先验收512KiB L1配置，失败时明确记录原因，再评估448KiB对照。

静态检查包括：flatId唯一覆盖、所有尾块地址、raw uint16 NZ布局、各槽事件收发配对、workspace分区和32B输出/尾写合法性。当前CPU模型已检查数学覆盖与布局，不代替这些源码审查。

### 步骤B：先过精度，再做很小的端到端筛选

从现有数据集复用固定输入、基线和计时方法，减少准备卡时：

- 首筛8组：M1280、N=4096/4160/5120/6080，两种TA，先FP16；N尾部与NFLOP均衡两端都覆盖。BF16先做精度，入围后补相同性能覆盖。
- 普通精度覆盖全部32个N、两种TA、两种dtype；特殊输入增加全负、零、重复列、不同尺度和K消去。输入应先按真实dtype量化，参考计算用CPU FP64。
- 同步与事件风险较高，普通数值通过后，对连续多次调用、不同输入替换、输出毒化、边界/尾部做检查；候选入围后运行mssanitizer可用的内存/竞争检查，保留工具局限，不把未通过检查写成通过。
- 时间取完整算子设备端耗时，包含所有归约与同步；同机串行 A/B/B/A 两个窗口，每窗30次丢弃5次，核对实际kernel名。不能只计稳定态Cube段或把host耗时当kernel时间。

### 步骤C：只对明确问题做一个对应消融

若首筛至少有稳定收益，再扩展32配置性能初筛及预先冻结的96配置独立N留出。不要一开始同时展开几十种调参组合。

|观测到的问题|最小对照|要回答的问题|
|首次B填充或跨run等待占比高|同一plan，完整B一次预载|6次分段是否不如一次大搬运；不能同时改分核|
|MTE1/驻留B读取效率差|同一128块和新分核，关闭B跨M复用|区别来自驻留布局/读取，还是其他新开销|
|末端同步/合并变慢|同一producer，串行与并行Max合并|新cores份partial是否值得多一次SyncAll|

关闭复用、整块预载等为本地研究对照；不因为局部图好看就生成多个Judge提交版本。

建议采用有实质幅度的入围标准：初筛中位耗时下降至少5%，两个窗口方向一致；若边界有超过3%的稳定回退，先解释并修复。达不到时，先用1～2个代表形状的profiling判断主因，最多做一轮对应消融，避免再次陷入无依据的常量扫参。这些是实验决策阈值，不是对未来结果的保证。

### 步骤D：只有入围后才发15点提交代码

独立留出、精度与资源/同步验收支持后，冻结源码、记录SHA256，提供完整 `v12_rxx_*.asc` 给用户做Judge15点。15点全部Pass、Case12有可复现收益且其他点无实质回退，才晋升。r41作为对照和回退始终保留。
