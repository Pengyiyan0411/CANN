# Case12 新探针结论：源码复核与离线实验计划

日期：2026-10-01。正式主线保持 `v12_baseline_r41.asc`，没有修改算子源码。本轮没有连接算力卡，没有执行CANN编译、NPU精度检查或性能测量。

依据是用户提供的《最重要的是第一条：Case12 的 K 已经精确确定为 1536.md》、r41实际源码、既有实验归档，以及本轮在本地CPU上执行的原样host planner枚举。新报告中的探针源码、原始输出及平台源码哈希本轮未取得，因此其命中/未命中按用户提供的新证据采用，不能称为全部独立复现。

## 1. 总体判断

**报告把下一步聚焦到producer的数据加载，方向合理；K1=192/256/320值得作为第一轮实验。** 但“已满占用”“已锁定B搬运瓶颈”“原分工下能跨M复用B”等表述需要收紧。

本轮最有实际价值的补充是：

1. 按新报告所有条件，原始planner确实只剩20/22/24三个核数状态。
2. **所有剩余状态均满足`pM=mTiles`，每个任务在M方向恰好只有一个宏块。** 在不改分工的前提下，简单交换M/N循环不能获得核内B跨M复用。
3. 如果比赛入口的`availableCoreNum`仍为此前实验环境对应的20，则**M也可以确定为1280**。此时只剩32种N、两种TA和两种dtype，已经可以设计很集中的本地验证集。

## 2. 新信息如何解读

|新证据|可采用的结论|边界|
|---|---|---|
|原K候选1536/1568/1600/1632；K_GE_1568未强响应|`K=1536`|要求同一路由、同一可靠强编码和前置K范围成立|
|TB_TRUE未强响应|`TB=false`|不能由此推出TA或dtype|
|r30强压力命中|当前Case12走`bmms1230`|采用报告结果；本地没有这轮原始探针代码|
|pN=2、pM≥8、tasks=blocks=cores|单波、逻辑任务数与核数相等|不等于MAC/MTE流水持续满载，也不证明每核用时相同|
|flatPeak==oldPeak；允许tie后117.01/116.88μs|当前不应把r41的`<`门槛直接改成`<=`|只说明这一种tie展平方案更慢，不排除其他任务顺序/geometry|
|A_LOAD_X2=135.58，B_LOAD_X2=146.66，基线113.67μs|对增加输入加载工作敏感，值得优先研究producer|不是各阶段时间占比，也不是删除一份加载必然节省的时间|
|RINGREAD_X2=118.39μs；rowmax/merge信号弱|ring低于A/B加载优先级，暂缓继续优化merge|弱信号不等于零成本；还需确认重复工作未被编译器消除|

K=1536时，当前K1=256确实只有六个完整stage；`k0==1536`的第七stage不会出现。P4/P5因此与未触发干预一致，**不能用它们的微小耗时变化估算tail加载成本**，也不构成独立于K探针的第二份tail证明。

报告中的89.22μs是新报告给出的参考成绩，本轮没有重新读取实时榜单；不把它当成已验证的同shape本地基准或可达下界。

## 3. 用实际planner复核shape和plan

直接从r41提取`bmms11r2`的host planner，未手工重写策略；其正文与r33对应代码一致。使用本地g++编译CPU枚举器，遍历：

```text
cores = 1..64
M = 1280,1296,...,1520
N = 4096,4160,...,6080
TA = false / true
B=1, K=1536, TB=false
```

共65,536组输入，过滤原资格、AlignedPitch以及新报告的plan条件，得到640组兼容的`cores/M/N/TA`记录；dtype不参与host plan，此计数未乘dtype。

|cores|pM|pN|mTiles|兼容M|兼容N|每任务M宏块数|
|---:|---:|---:|---:|---|---|---:|
|20|10|2|10|**1280**|4096..6080，步长64|**1**|
|22|11|2|11|1296..1408，步长16|同上|**1**|
|24|12|2|12|1424..1520，步长16|同上|**1**|

TA=true仍需M%64=0；上表M列是两种TA的并集。AlignedPitch完整条件是：

```cpp
(!ta || M%64==0) && ((tb ? K : N)%64==0)
```

TB=false只把第二项化为N%64==0，不能删除TA相关的第一项。M=1280时两种TA均满足。

**条件式结论：若比赛传入cores=20，则`(B,M,K,TB)=(1,1280,1536,false)`，N为32个64对齐候选。** 过去本地卡是20 Cube，但`run_kernel`实际采用调用方传入的`availableCoreNum`，不能直接用本地硬件信息证明Judge也传20。恢复环境后优先核对已有合法日志/入口参数，而不是先花4次探针二分M。

若有必要继续精确N，32候选最多5次自适应二分；做优化本身无需先精确N。精确shape并不等于TA和dtype也已确认。

## 4. 最重要的架构修正：当前没有核内跨M复用机会

对上述所有兼容状态：

```text
B=1
tasks=blocks=cores
pM=mTiles
每个核组只执行一个task
每个task在M方向只负责一个128行宏块
每个task在N方向连续处理多个256列宏块
```

所以原`for(m0) for(n0)`中的M循环只执行一次。B面板跨不同M行块的重复加载发生在**不同核组**，不是同一核内的连续M宏块。

- 不改plan，只调换M/N循环：不会消除这些B加载。
- B全K驻留在单核L1：在当前分工里没有第二个M宏块可复用。
- 真正的核内B复用需要改任务归属、增加单核M覆盖、改变AM/BN或重排K/M/N并管理多个C累加器。
- r30每个128×256的FP32 C累加器已占128KiB L0C；两个完整同尺寸累加器需要256KiB，不能假设当前资源方案可直接容纳。
- 跨核重复请求可能由缓存部分吸收，逻辑GM→L1字节数不等于实际HBM流量。没有缓存数据时不判断L2命中率。

在20核、M1280条件下：

```text
nTiles = ceil(N/256) = 16..24
每核N宏块数量 = 8..12（奇数nTiles时两类N分片不同）
总A逻辑加载字节 = M*K*2*ceil(N/256)
总B逻辑加载字节 = 10*K*N*2
最终partial = pN*M*4 = 10,240字节
```

这解释了为什么“只改B驻留”与“改变AM/BN减少跨M重复”是不同实验。即使只有10KiB partial，也不能仅凭小字节数宣称最终同步零成本。

历史v12_r45已尝试B全K面板驻留、128列子面板、原任务归属，启用的10配置全部回退，中位−14.82%。该旧实验不证明所有B复用架构都无效，但新plan信息进一步削弱了重复这条路线的理由。

## 5. K1实验可行，但不是纯粹的stage数量因果实验

保持AM128、BN256、K0=64、FP16/BF16输入、A/B双缓冲时：

|K1|K段分解|stage数|A+B加载调用/宏块|MMAD次数/宏块|A1+B1|结论|
|---:|---|---:|---:|---:|---:|---|
|192|192×8|8|16|24|288KiB|适合做较小stage对照|
|256|256×6|6|12|24|384KiB|当前基线|
|320|320×4+256|5|10|24|480KiB|可按当前512KiB预算准备，仍需真实编译确认|
|384|384×4|4|8|24|576KiB|**超过当前512KiB L1预算，不能原样只改常量**|

资源公式：`2个槽*(AM+BN)*K1*2字节`。L0A/L0B/L0C在前三版保持32/64/128KiB。上述是显式分配模型，不是CANN编译器资源验收。

前三版的K0累加片段都是`0,64,...,1472`，共24次；每个完整空间宏块的A/B逻辑数据量分别为384KiB、768KiB。因此实验保持数学工作量和请求数据量，改变L1 stage组织。

需要重点审查320版：

1. stage数为奇数，跨宏块预取的L1起始槽会交替；192/256版为偶数stage，不交替。原代码通过`l1Start`处理，但改版仍应验证READY/FREE生命周期。
2. 最后stage的实际kr1=256，不能把所有L1→L0地址步长都常量化为320。当前代码用kr1参与NZ索引。
3. 更大K1还改变DMA块大小、L1占用、预取提前量和排队行为；不是只删两次event。

因此：若320更快，支持“stage组织优化有效”，不能唯一证明setup成本主导；若三版持平，也不能反向证明一定是带宽主导，可能是多项收益与代价抵消。

## 6. A/B sensitivity不能直接决定收益上限

报告增量为：

```text
A_LOAD_X2: +21.91μs
B_LOAD_X2: +32.99μs
RINGREAD_X2: +4.72μs
```

完整宏块本来就有`B字节数=2*A字节数`。B重复加载的绝对扰动更大，支持先调查B侧，但**不能据此断言B每字节效率更差**。这些结果也不等于A/B/ring的可消除耗时，更不能线性外推“B少搬一半可节省16.5μs”。

重复DMA可能改变共享MTE2资源、L1槽等待、缓存状态和计算重叠。源码中的A/B加载共用stage READY，因此最合理的当前判断是：**输入加载与流水组织是高优先级候选瓶颈，B侧有较强绝对敏感度；具体机制未定。**

“tasks=cores”只说明逻辑计划覆盖所有核组，不等于流水满载。就算宏块数达到计数下界，N尾块、布局、DMA等待仍可能造成完成时间不均衡。

## 7. 修订后的优化顺序

### 第一轮：K1=320对照256，192作为机制对照

保持原planner、AM/BN、K0、consumer、ring、完整K累加与最终Max/Sum不变。新路线依据运行时K/layout/plan选择，所有输入值均参与原语义计算；不按测试点编号、内容或跨调用状态分派。

先静态审查地址与事件，再做真实CANN编译和数值验证；性能测试必须包含完整kernel的预取/消费流程。不能只用LoadStage小片段计时宣称Judge收益。

### 第二轮：在新窄范围重新评估AM256×BN128

这不是全新的方向：v12_r29已经测过，中位仅+0.47%，最差−33.42%。重试需要解释与旧实验的区别：保留已有效的r30跨宏块预取，限定新的合法元数据域，并关注M1280恰好256对齐、K1536、TB=false的子域。

在M1280情况下，M宏块数由10变5，B重复请求约减半；N宏块数约翻倍，A请求约翻倍。完整对齐空间下，二者总逻辑字节数基本不变，这是A/B流量分配与实际搬运效率的取舍，不是总带宽量无条件减半。planner、L0布局和尾部成本必须重新验证。

### 第三轮：B布局整理或新的跨M复用架构

若计数器仍支持ND→NZ/加载侧，考虑B单侧预整理NZ作为独立候选，让不同M核组读取已整理的数据；它减少的是重复格式转换机会，代价包括预处理、额外GM写读、workspace与同步，并不自动减少各核读取B的字节数。Case8的成功只能提供设计参考，不能直接保证对齐Case12也获益。

真正B-stationary则必须与新任务分工和累加器容量一起设计。不能继续把“只交换原循环”作为复用方案。

### 暂缓

- 再次放宽r41 tie门槛。
- 单独rowmax/partial/merge小改。
- 已被K1536排除的第七K-stage假说。
- 不变任务分工的B全K驻留。

这次新证据提高了Case12验证的针对性，可以给它一轮低成本K1筛选。但不能据此宣称Case12已经比2/3/4更容易提分，整体优先级仍需看真实收益与实验成本。

## 8. 恢复算力后的最小实验集

若确认比赛及本地均传20核，固定`B1/M1280/K1536/TB=false`：

1. **初筛32配置**：N取`4096,4160,4480,4800,5120,5440,5760,6080`，两种TA、两种dtype。覆盖完整N宏块以及64/128/192列尾部、奇偶N宏块数和宽度两端。
2. **独立留出96配置**：其余24个N，各两种TA和两种dtype；在初筛决策前冻结输入/种子，不拿初筛赢家充当留出。
3. 每个候选先通过数值验证，包含全负、零、不同幅度与消去输入；性能串行A/B、B/A独立窗口并核对实际kernel命中。基线是同机r41，不是89.22μs的未知实现。
4. 只给初筛优胜者做完整留出、必要内存/竞争检查及15点Judge回归。保留1–15非目标路径；微小单轮波动不晋升。
5. 若核数仍不确定，应覆盖上表22/24对应的合法M/TA组合，或者先确认cores；不要把20核结论直接写死进算法。
