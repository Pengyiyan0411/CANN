# R43_CASE8_PADDED_MACRO：收益解释与下一步

2026-09-27。本次任务是分析下一步，未修改 R43 或 R25，未生成新提交内核。

## 1. 结论

用户反馈：Case8 从约 **91 μs 降到 62.45 μs**，其他点基本不变，变化处于测评波动范围。以约 91 为参照，耗时下降约 **31.4%**，速度比约 **1.46×**。原始 15 点表、重复次数和平台编译源码摘要未提供，不补造这些数据，也不将近似基线写成精确统计结果。

**建议把 R43 固定为下一轮 Case8 的性能对照，同时保留原字节 R25 作为回退。** 下一步优先减少 R43 新增的输入整理和内区消费开销，保持现有 Macro 生产端、K0=64 双 L0、环形包协议和 guard 不变。不要因为这次成功，立即扩大全部 ragged 输入的覆盖域或重新放大 MMAD 粒度。

R43 最有价值的证据是：通过小幅补齐，让原本被对齐门槛排除的输入复用成熟 Macro 路径，可以带来明显收益。它支持先修复快路径覆盖缺口的方向；没有证明 62.45 μs 的剩余瓶颈已经是 padding、Cube、C 搬运或最终归约中的某一项。

## 3. 本次对 Case8 的新定位

R43 的 `Eligible` 只接受：

```cpp
B == 1
1024 <= M && M < 2048
1024 <= N && N < 2048
1024 < K && K < 1280
K % 8 == 0
M % 16 != 0 || N % 16 != 0 || K % 32 != 0
dtype 为 FP16 或 BF16
```

在这份源码对应本轮成绩的前提下，结合明显改善，Case8 的工作画像可推进到：

**单 batch、中大型 M/N、K∈{1032,1040,…,1272}，至少一个 M/N/K 对齐条件不满足的 dense。** semantic family 为 `Dense_LargeK`。还不知道精确 M/N/K、各自余数、TA/TB 和 dtype；尤其不能把“至少一项不对齐”写成“三项都不对齐”。

原 R25 的 Macro 和 R03 都要求 M/N 16 对齐、K 32 对齐，因而不覆盖此集合；Split-K、Native、Tiny/Resident/skinny 也不覆盖。原执行会进入 V7.1/V4.3 generic portfolio。该 portfolio 还会尝试其高阶 Matmul fast 路径，不成功再用 GM stripe safe 路径；没有精确 N 和运行时 tiler 结果，不能进一步断言原来一定是哪个底层 kernel。

## 4. R43 为什么有效

```text
AIV：原始 A/B → 位拷贝到补齐后的 GM A'/B'
       ↓ 全 AIV 就绪屏障，再通知 AIC
AIC：原 R25 Macro 生产端，完整 K 累加 → FP32 C ring
AIV：消费 C ring，只让真实 N 列参与 max
       ↓ 跨 N 分片合并
最终：仅对真实 M 行求和
```

补齐尺寸为 `Mp=ceil(M/16)*16`、`Np=ceil(N/16)*16`、`Kp=ceil(K/32)*32`。A/B 保留各自原物理布局，TA/TB 继续交给原 Cube 模板；这不是转置，也没有把 BF16 转成 FP16。有效数据按原始 16-bit 字复制，新填充区写同位模式的零。

此 guard 范围内，补齐导致的数学计算体积比 `Mp*Np*Kp/(M*N*K)` 最大约 **1.053424**，即最多约 **5.34%**。这是逻辑计算体积上界，不是实测时延开销。少量冗余计算换来成熟分块、输入复用和流水，足以解释为什么“多做了预处理”仍可能比旧路线快。

R43 已正确保留两个数学边界：新增 N 列的 C=0 不能参与行 max，否则全负输入会错误选中零；新增 M 行不能进入最终 sum。其消费端用 −∞ 屏蔽无效 N 列，并按 `realM` 求和。后续不能为减指令删掉这两项。

## 5. 剩余开销：源码能确定什么

### 5.1 输入补齐完全位于 Cube 计算之前

`Entry` 中 AIC 在 `PACK_TO_CUBE` 等待后才调用 `ReuseProducer::Process()`。AIV 必须先完成整个 A/B 的整理和全 AIV 屏障，再释放 AIC。

因此端到端包含一段独立的 packing 时间，随后才进入 Cube/消费重叠段和最终合并。**当前不能把 packing 与 Cube 已经重叠当作事实。** 但也不能在没有分阶段计时的情况下说 62.45 μs 主要耗在 packing。

`PACK_ALL` 保证各组整理的数据全局可用，`PACK_TO_CUBE` 再交接给本组 AIC；由于数据整理按全局 job 分配，AIC 所需的数据可能由其他组生成，不能直接删掉全局屏障。官方模式 0/2 分别约束全核与组内 AIC/AIV 就绪关系，R43 的 batch 调度也应保留。[官方 CrossCoreSetFlag 文档](https://asc.gitcode.com/api/SIMD-API/basic_api/sync_control/inter_core_sync/CrossCoreSetFlag_ISASI.html)

### 5.2 两个输入无条件复制，部分输入可能本来就不需要整理

当前 A 和 B 均分配补齐副本、产生 pack job。可以分别判断物理描述是否完全一致：

```text
A 可以直接复用原指针 ⇔ M%16==0 且 K%32==0
B 可以直接复用原指针 ⇔ N%16==0 且 K%32==0
```

这两个条件适用于四种 TA/TB，因为相应两个维度均未变化时，物理行数、列数和 stride 均不变。当前 ragged guard 下不可能两者同时完全不需整理。

若 Case8 的 K%32≠0，两侧均不能走这个省拷贝条件；当前没有证据确定其余数。因此它是值得实现的自然元数据策略，但不能预告 Case8 一定受益。也不能只在整块矩阵末尾添零：物理列跨度变化时，每一行都必须按新 stride 排列。

### 5.3 每个 pack job 都先整块清零，随后大部分位置被输入覆盖

`PackInputs` 当前每轮执行：

```text
Duplicate(整个输出块, 0)
→ 拷贝全部真实行及显式行尾 padding
→ 写出整个补齐块
```

可省的是有效数据区的重复清零；需保留的包括补出的整行、以及 DMA 没有覆盖的行间空隙。对完整真实行且 `dstCols==ceil(srcCols/16)*16` 的 job，搬入操作已经覆盖整个目的行，整块预清零有机会去掉。

一个容易遗漏的边界是：K 补到 32 元素，而半精度 DMA 行只先补到 16 元素；当 **K%32 为 8 或 16** 时，二者之间可能还剩 **16 个半精度元素，即 32 B** 的间隙。不能仅删除 Duplicate 后假设那里会自动清零。填充必须使用显式 paddingValue，不能依赖 dummy 区内容。[官方 DataCopyPad 文档](https://asc.gitcode.com/api/SIMD-API/basic_api/memory_vector_compute/data_move/DataCopyPad_GMToUB.html)

下一版应只对整行尾部/间隙清零，并继续维护搬入、搬出和槽复用依赖；先保持现有双槽和屏障协议。

### 5.4 内部完整 C tile 也付出了尾列处理成本

`MaskedRowMaxConsumer` 对每个 micro-tile 都先将接收区填成 −∞，再执行带 padding 描述的搬运。对于 `live==TN==128` 的完整 tile，真实数据会覆盖接收区全部有效位置，−∞ 预填充是多余工作的候选。

可分成两条消费路径：完整 128 列直接搬运；最后一个不完整 tile 保留显式 −∞ 掩码。在本范围内，不完整 tile 至多是每行的最后一个，不能把所有 tile 都当尾块处理。此改动不改变 C ring 布局、Mmad、N 分片关系或最终 realM 求和。

这项独立于“哪个维度不对齐”，适用性比省掉某一个输入副本更广。它减少的是清填和控制开销，并不消除 C 的 GM 写读；能否降低时延仍需实测。

### 5.5 packing 并行度与原 Macro planner 有耦合

pack 的 worker 数固定为 `2*p.cube.blocks`，但 `p.cube` 来自原 Macro 的 `MakePlan`。后者按计算块峰值、输入量、波次等指标选网格，不知道 packing 的 job 数。部分组合会少用核，从而让 packing 多出一轮 job；整个 Cube 都要等最慢 pack worker。

源码提取后的 host 枚举确实找到这种组合，但**没有证明实际 Case8 的计划属于其中之一**。因此，下一阶段应联合考虑：

```text
每 worker 的 pack job/字节负载
+ Cube 最大任务工作量
+ 尾波与 N 分片合并成本
```

不要直接把 blocks 强制设满，也不要修改全局 `bmms11r2::MakePlan`：那会重新触及 R25 的 Macro 点。若试验联合 planner，应仅用于 R43 域，并保持生产/消费分片一致。

## 6. 建议的下一轮：三个独立消融，再决定是否动调度

下面是候选设计标签，并未生成对应 `.asc`。每一项独立从原 R43 出发，避免收益/退化混在一起。

| 顺序 | 候选方向 | 改动边界 | 需要回答的问题 |
|---|---|---|---|
| 1 | `PACK_TAIL_ZERO` | pack 只清新增整行和未被 DMA 覆盖的 gap；保留显式 padding、双槽与所有交接 | 当前整块清零和相关 V 流水是否构成可见开销？ |
| 2 | `C_INTERIOR_FAST` | `live==128` 用完整块消费；只有尾列使用 masked path | 泛化尾部处理是否在大量内区块上付出明显代价？ |
| 3 | `PACK_IDENTITY_SKIP` | A/B 分别判断描述一致时直接用原指针；只整理真正变化的一侧 | Case8 是否具备省掉整侧搬运的条件，且收益是否可重复？ |
| 后续 | R43 域内联合 planner | 把 pack 的最大 job/字节量纳入计划选择，保留 Cube 原形状 | 降低计算峰值的计划是否反而拖慢全量输入准备？ |

前两项覆盖当前 guard 内的大部分正常 tile，且保持计算次序，优先级高。第三项可能省掉较多逻辑搬运，但能否命中 Case8 取决于未知余数，因此单独测试，不与前两项绑定。

如果这些消融均无收益，不继续无限调 buffer 大小。可增加一个正确性保持的 packing 放大对照：在发出**唯一一次**最终 pack→Cube 就绪信号前，重复相同 packing 工作，用延迟增量观察该阶段是否敏感。不能直接把整个 `PackInputs` 调两次，因为它内含跨核 signal/wait，重复调用会改变协议。增量会受缓存影响，也不能直接当成精确阶段耗时。

只有确认全量输入整理占比显著后，再研究按 panel 整理并与 Cube 重叠。那会涉及新的 ready/credit、数据归属和双缓冲，风险和工作量都远高于前三项，不宜作为紧接着的一版。

## 7. 当前不建议做的事

- 不把 R31 的 K0=128 单 L0 再叠加进来；它已出现退化，R43 的成功使用的是原 K0=64 双 L0。
- 不将 M/N 一步补到 128/256、K 补到 256 的大块边界，除非先核算并证明值得；当前 16/16/32 的计算膨胀上界很小，大补齐可能明显增加工作量。
- 不因当前 Case8 好转就扩大到所有 B、所有 M/N/K 尾部；先把当前 guard 的独立收益稳定保住。
- 不在未确认阶段占比前改成 C-free、全新融合 MMAD 或直接删除全局屏障。
- 不把“按元数据隔离”写成硬件性能保证；每次仍保留全 15 点检查，尤其检查与新 guard 可能相交的未知点。
- 不通过缓存上次输入、读取测试编号或参考结果跳过真实计算；所有选择继续只依赖输入元数据。

## 9. 下一次验收口径

以 **原 R43 的约62.45 μs** 为 Case8 新对照，不能再用 R25 的约91 μs 宣传后续候选收益。每个独立消融先通过精度，再交替测 R43→候选→候选→R43，并记录完整15点。保留可重复的改善，用户报告有其他点退化则不晋升。

当前最值得延续的是“输入正规化后复用成熟快路径”这一结构性成果；紧接着的一步是缩减这层适配和边界处理的冗余工作，并用独立消融确认剩余瓶颈。
