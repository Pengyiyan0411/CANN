## 为什么选择点3/4

历史诊断报告给出点3/4为 `B>1、2<=M,N<=16、K<=128`，与点2主要相差 batch 数。该报告的原始 Universal 探针尚未独立复核，精确 M/N/K、B 和布局仍未知。R50点2实测5.01/5.06微秒，支持尝试复用其计算组织，但不能保证多batch会有同等幅度收益。

点6路线证据较弱，点12尚缺区别于9/10的几何和布局证据；本轮先做可从已有效计算方式直接扩展、且容易限定影响范围的点3/4。

R50两次点3为5.29/5.14、点4为6.50/6.42微秒；这是本版的近期对照。[全部15点原始读数和图片](../V11_results/2026-09-28_r50_feedback/RESULTS.md)。

## 接管范围与实现

```text
2 <= B <= 64
2 <= M,N <= 16
32 <= K <= 128，K % 8 == 0
原来属于 Tiny/Resident（在此域内等价于 M*N*K <= 16384）
```

只接管这组输入元数据。精度包括FP16/BF16，布局包括NN/NT/TN/TT。

- 保留旧 Tiny/Resident 的 `workers=min(B,2*cores)`。一个 AIV 依次处理 `batch=id,id+workers,...`，不增加跨核汇总。
- 每核只初始化一次 UB 和 gather 索引，连续处理多个batch时复用；输入输出队列在各batch内分配和释放。
- 每个batch采用R50的分阶段计算：全部点积乘法、点积归约、行最大值、最终求和。不同点积采用独立产品空间；Tiny的归约scratch也独立。
- 保留原 Tiny 的 `ReduceSum(K)`，以及 Resident 的128→64折叠/`WholeReduceSum`；保留最终FP32行求和。
- 一个kernel，无GM workspace、显式host同步或跨核屏障。每个输出只由一个batch owner写入，精确写4字节。

B=1的R50点2不进入本版新模块。点5要求的N≥32、点7的K≥256、点8的大形状、点13/14的大M或N、点15的长K均与此域不相交。源码级分派不变不等于实测完全无波动。
