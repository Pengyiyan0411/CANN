# BMMS V12：同比赛环境 NPU 验证与实验计划

日期：2026-09-28。本文为待执行方案，不是已经获得的 NPU 实验结果。

## 1. 目标和当前起点

目标是提高单位租卡时间获得的、可在比赛复现的有效收益。优先建设一次性的自动闭环，再进行少量有依据的结构实验；不以提交版本数或设备占用率作为成功指标。

- 冻结主线：`v12_baseline_r03.asc`，SHA256 `1c9e9726aa43fdd177c98c645c69bb7d57721d2f1b07d00dfb614324286a404c`。
- 第一候选：`v12_r06_case9_macro_mmad.asc`，SHA256 `9b372b1535dd0c9d3156675e241ca0c69f74102463b76bd7e449d655820fb64e`。
- r04 的 Case9=69.09 μs，仅说明部分 A 缓存没有明确收益，不证明搬运不重要。
- r05 的 Case9=765.68 μs 为压力探针结果，证明完整分派条件命中，不能作为性能基线。
- r06 目前只有 CPU/host 验证，没有设备编译、精度或性能结果。第一轮必须补齐。
- 历史 15 点截图用于确定量级与保护已有成果；每个实验仍需同时段 r03 对照。

## 2. 首先区分环境与用例

### A. 原始 15 个用例和比赛 runner 均可用

直接使用原用例。一次离线 host 记录提取 B/M/N/K、dtype、TA/TB、stride、broadcast、route、pM/pN、tasks、blockDim、tile、K0/K1、workspace 和 kernel 序列。日志不进入计时路径。

停止用耗时猜 shape，也停止已有用途的二分压力探针。性能分派只能基于输入元数据，不读取正确答案或依赖测试编号。

### B. 只有相同硬件、软件环境，拿不到隐藏用例

同环境不能恢复隐藏 shape。将已有确定条件、推测和未知分开记录，建立约束范围内的代表用例。结论称为“该 shape 簇有效”，不能称为“已优化比赛 CaseX”。

- Case9：r05 已确认的 B=1、M/N≥1024、对齐、1024≤K<1536，以及原 plan 的 N 方向复用门槛。
- Case10：不能仅凭与 Case9 耗时相近就用相同守卫；r05 未产生压力响应。
- Case12：已知 B=1、M/N≥1024、1536≤K<2048 及 R06 对齐条件。
- Case13/14：从原探针文件核对 Native 条件后建立集合；Case13 的 M>256 若没有独立确认，继续标记为假说。
- Case6：route 未充分定位，先在合成输入中记录实际分派；不伪造其精确形状。

每个目标簇先选 12–24 个性能用例：覆盖长宽比、tile 整除/尾块、planner 台阶、K 边界，并通过覆盖设计纳入 dtype/转置。不是全部变量的笛卡尔积。另留至少 1/3 的用例只做后期验证，防止对调参集过拟合。

候选区间示例为 M/N={1024,1536,2048,4096} 的方形与长方形组合、K={1024,1280,1504}；资源允许时补上大空间边界。它们只是实验样本，不是对隐藏用例的断言。正确性集合另加非满宏块与守卫内外邻点。

## 3. 卡开始计费前完成的工作

1. 固定算子数学语义、比赛精度规则、输出 dtype 和输入支持域；从 runner 核对计时和评分公式。
2. 保存源码、编译命令、CPU 检查和资源预算。r06 当前本地检查直接复用，不重复铺开同类测试。
3. 准备统一 launcher：baseline/candidate 可选、明确符号与产物路径，避免动态库缓存导致运行旧版本。
4. 准备参考结果、固定种子和 JSONL 用例；缓存参考结果时将输入生成方式、dtype 与 seed 纳入键。
5. 准备编译缓存、实验清单、超时处理、报表模板。编译缓存键包括源码、头文件、编译器版本、flags 和 SoC。
6. 默认每次只有一个 NPU 性能任务。编译在 CPU 上并行，但限制 CPU/内存竞争；最终计时暂停重编译。

本计划不要求升级环境或重建整个工程；优先复用比赛的最小编译/调用方式。

## 4. 接入后的环境验收（约 10–20 分钟预算）

记录具体 SoC/步进、AIC/AIV 数量、驱动/固件、CANN/compiler、运行库、编译目标/flags、设备内存、资源限制和电源/时钟策略。检查设备独占情况与温度/频率是否稳定；不擅自改变比赛配置。

用比赛命令编译 r03，跑代表小、中、大输入。若 r03 不能通过，先修复复现链路，不带着不可信基线继续调参。再编译 r06，记录首条编译错误及完整日志。

若本地原用例与比赛耗时不一致，先查计时范围、kernel 数、异步同步、热身、数据缓存和编译选项。一个统一的倍率不能证明复现成功。

## 5. 正确性门槛：先排错，后计时

### 5.1 分层检查

- 冒烟：8 个左右小用例，覆盖 FP16/BF16 和四种 TA/TB。发现编译、布局或输出异常立即停止该候选。
- 初次结构改动：至少 30 个设备正确性用例；包含满/尾宏块、多个 K stage、多任务、ring 多轮复用、完整真实尺度和守卫边界。
- 候选精测前：目标真实用例或完整目标簇正确性通过。
- 晋升前：15 点（若可用）及固定的跨 route 回归集全部通过。合并多个候选后重跑集成测试。

### 5.2 必须覆盖的数值和同步问题

- 零输入、全负输出、正负抵消、多指数尺度、相近行最大值、不同随机种子；只在合法输入域内测试极值。
- 小矩阵用从实际输入 dtype 转换得到的 FP64 独立参考；大型输入使用核对过的参考路径并抽查行/块，避免全量 CPU FP64 成为卡时瓶颈。
- 比赛判定标准是最终门槛。不能把框架默认容差或与 r03 一致代替独立正确性。
- 调试构建检查 matmul/row-max/最终 sum 中间值，计时构建删除这些观测写入。
- 连续多次调用，交替 shape，复用 workspace，并在允许的写入区填充不同旧数据，检查遗漏初始化和陈旧 ring 数据；不能只依赖清零内存。
- 对新增索引/同步路线选择少量边界例运行环境支持的内存检测；通过后不对每个参数组合重复重型检测。

### 5.3 不可破坏的数学顺序

先完成 K 维累加，再在完整 N 域取每行 max，最后求行和。N 分片可先得到局部行 max，再合并；K 分片必须先合并矩阵部分和，不能先对每个 K 分片求 max 再相加。全负输入的 max 初值不能错误使用 0。

## 6. 两套测量：排名与诊断分开

### 6.1 正式性能计时

尽量逐项复刻比赛 runner 的计时范围：预处理、workspace、kernel 序列、最终归约哪些计入，必须一致。kernel-only、整个算子 device 时间、host wall time 分列，不混成一个指标。

计时前完成编译、分配、输入生成、参考计算、日志。采用环境支持的 device events 或比赛计时接口，等待完成后再读时间。Event 包住 Python 连续提交也可能包含设备等 host 的空隙，因此用短 trace 检查提交间隙，不把墙钟或 event 结果自动视为纯 kernel 时间。

若比赛逐调用同步，本地保留同模式；不能仅凭批量回放去掉 host 开销后得到的名次晋升。图回放仅在比赛同样使用或作为明确标记的辅助诊断时启用。

默认测量起点（均可依据实测稳定性缩短/加长）：

| 阶段 | 采样预算 | 用途 |
|---|---|---|
| 校准 | 50–100 次热身；r03 对 r03 的交替窗口 | 测量重复性、漂移、缓存和计时下限 |
| 快筛 | 5 个成对窗口，每窗口约 2–5 ms 的有效运行量 | 淘汰明显无效/退化方案 |
| 精测 | 20–30 个成对窗口，每窗口约 10–20 ms | 估计收益和稳定性 |
| 最终复验 | 新进程、独立一轮、最终单文件产物 | 排除偶然最优、缓存与集成影响 |

上述重复时间不是对 profiler 的配置。采用 ABBA/BAAB 顺序，其中 A=r03、B=候选；记录窗口均值、中位数、分位数、配对比值。原始逐次事件的粒度若低于测量分辨率，改用可比的批量窗口，但仍需比赛模式复验。

统计单位是独立测量窗口，不把同一循环中的上万次调用当作上万个独立样本。对配对窗口的 log 加速比做 bootstrap 区间；调参后用未参与选择的复验结果裁决，降低“挑最快样本”的偏差。

缓存策略与比赛一致。额外准备同地址热缓存与轮换输入两种诊断；后者只有工作集实际超过相应缓存时才可讨论冷数据，不能直接叫“清空 L2”。记录实际工作集。所有方案对比使用相同种子、布局和缓存模式。

### 6.2 瓶颈 profiling

先只采 r03/r06 的一个命中例，再补一个尾块/另一布局。不要给每个参数组合开 profiler。

- `msprof op` / 环境提供的单算子工具：选取支持的 PipeUtilization、Memory、L2、L0 和冲突指标；具体名称、支持范围先通过该 CANN 版本 help 确认。
- timeline：核启动、AIC/AIV 重叠、MTE 与 Cube 空洞、ring 等待、最后归约、各核完工差。
- 如使用 torch_npu.profiler 的技能报告路径，使用 warmup=5、active=5 的采样配置，并报告 custom 与 NPU 参考路径；该路径用于诊断，不替代上面的正式计时。
- 指标可能需要多轮采集，分开采；不要期待单次拿到所有计数器。
- 只在解释不清布局/指令依赖时用 simulator。模拟时间不作为板上性能成绩。

不要把各条流水的 busy 时间直接相加成总耗时，它们可以重叠。producer-only、consumer-only 或删除同步的实验会改变执行关系，只能辅助定位，不能用两个数相减得到可靠的瓶颈占比，也不能作为可提交优化。

## 7. 第一轮：r06 假设检验

假设：原 R06 把完整宏块拆成多条小 MMAD 造成有意义的指令/调度开销。

首先比较冻结 r03 与现有 r06，两者 grid、K0=64、K1=256、ring、归约保持一致。r06 将完整 128×256 宏块每 K0 切片的 MMAD 从 4 条变 1 条，同时合并 B 的 L0 加载，所以初次 A/B 证明的是整个包的效应，不能单独归因于 MMAD。

1. 在真实 Case9（可用时）或满足完整守卫的代表 shape 上验证实际选中了新入口。
2. 检查输出、尾块 Fixpipe 源步长、L0 布局和双缓冲依赖。
3. 快筛，再给幸存者做精测和最少量 profile。
4. 有收益后，再测试另外两档合法宏块（例如 128×128、64×256）；必须完成各自 L0/ring/尾块适配，不能只改一个维度常量。
5. 若要区分 MMAD 与 B 加载贡献，另做固定完整布局但拆分 MMAD 的合法消融；没有正确实现前不宣称因果分离。

决策分支：

| 实测情况 | 下一动作 |
|---|---|
| ≥5% 且稳定 | 完整验证；评估是否扩展到 Case10/11/12 对应 shape 簇 |
| 约 1–5% 且可重复 | 可以保留候选，但不继续无依据大扫；依据 profile 选择下一变量 |
| 与噪声相当或退化 | 保留 r03；看 Cube/MTE/Vector/同步哪条在关键路径，换结构方向 |
| 只在特定形状/布局收益 | 用元数据收窄守卫，在留出用例验证；不全局替换 R06 |
| 正确性失败/挂起 | 停止计时，保留可复现输入和日志，优先修复 |

5% 是这一轮“值得投入后续时间”的初始工作阈值，不是收益承诺，也不是排除小点高性价比优化的硬规则。

## 9. 评分与晋升

先核对真实公式。若各点等权几何平均加速比，优化的增量目标是：

`delta = sum_i(log(t_baseline_i / t_candidate_i)) / 15`

对应总体倍率 `exp(delta)`。单点快 20% 对总体约为 `1.2^(1/15)-1 ≈ 1.22%`，与该点原本 5 μs 还是 120 μs 无关。若平台按总耗时或其他公式计分，必须换成对应目标，不能直接套用。

选择下一实验可参考：成功概率 × 预期评分增量 /（编译、运行、分析所需的剩余时间）。这些是调度估计，不把主观概率当作实测统计。

晋升需同时满足：

1. 比赛精度规则通过；设备边界与持续调用检查通过。
2. 独立复验的评分改善稳定，主目标收益区间不跨 0。
3. 非目标点不存在可复现退化；先用同日 baseline 对 baseline 的波动定阈值。初始预警可用 max(2%, 3×相对噪声尺度)，但它只触发调查，不代表允许阈值以下真实回退。
4. 最终交付的单文件按比赛 flags 重编译，再验证实际分派及全套表现；不能只测实验开关版。
5. 若只有合成用例通过，保持“候选”状态，比赛反馈通过后才宣布比赛 SOTA。

确认退化时优先收窄守卫；若无法同时保留收益和正确/稳定表现则不合入。不要为了提高一项平均值隐藏其他点的退化。

## 10. 卡时调度和止损

单卡运行队列：正确性 → 快筛 → 精测 → 选定 profile → 最终复验。多个实验进程不能同时在同卡争用；不同卡可独立工作，但 A/B 必须在同一物理卡比较。

CPU 同时准备下一批构建、分析旧 trace、计算参考；传输和编译失败在入队前处理。租卡若包含等待时间，应提前准备环境镜像/依赖，并缓存产物。优化的是整段付费墙钟，不只是 kernel active 时间。

自动止损：

- 正确性失败立即退出该候选，保留输入、seed、route、版本和日志。
- 超时阈值从正常基线和首次编译区分设定；同步挂起中止任务，只有确认设备恢复后才接下一项。
- 在大多数代表样本明显退化的方案不进入全套精测。
- 连续三轮没有产生超出噪声的收益，暂停该方向；只有新 profile/新假设才重新开启。
- 同一 SHA、环境、case manifest 已经验证的项目不重复全量运行；改变 flags 或集成代码则重新做必要检查。
- 不因卡还空闲就运行没有决策价值的扫描；把剩余卡时留给复验、泛化和集成。

### 首个 4 小时会话预算（可调整，不是耗时保证）

| 时间 | 内容 | 必须得到的产物 |
|---|---|---|
| 0–20 min | 环境验收、r03/r06 设备编译 | 版本、编译日志、可运行基线 |
| 20–45 min | 精度冒烟/边界、A/A 噪声、计时校准 | 精度报告、计时可信度 |
| 45–75 min | r06 A/B、关键 profile | 保留/放弃及瓶颈证据 |
| 75–145 min | 第一个高收益方向的 3–6 个候选 | 1–2 个幸存者或明确否定 |
| 145–190 min | 第二个独立方向 | 增量候选；不依赖第一个成功 |
| 190–220 min | 合并、留出用例、全量回归 | 可提交单文件及回归表 |
| 220–240 min | 独立复验、归档、预留排错 | 最终候选、证据、下一轮方向 |

若只有 1 小时：环境/基线 15 分钟，r06 正确性 15 分钟，A/B+最小 profile 20 分钟，归档 10 分钟；不同时开三条新内核。若有一整天，增加第二轮迭代和留出验证，不按比例扩大盲扫组合数。

```text
reports/                   对比、晋升决策、失败方向
```

每个 run 记录源码/产物/用例哈希、parent、唯一改动、shape、dtype、转置、stride、route/grid、workspace、编译选项、精度误差、缓存/计时方式、设备状态、原始窗口、加速比及区间。Profiler 技能报告另保留 custom 与 NPU 参考对照；NPU 参考的时间不是排行榜最佳时间。

会话结束交付：一个明确的主线或保持原主线的决定、一个最终可提交版本、完整回归表、每个候选的去留理由、瓶颈截图/数据，以及无需重复的失败实验清单。不能只交付“最快单次时间”。
