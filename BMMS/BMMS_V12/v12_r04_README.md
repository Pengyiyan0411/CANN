## r02哪里有代价

这里区分源码事实与性能假说。已经确认实测轻微劣化；没有NPU profiling，因此不能宣称某一条指令是已证实的根因。

| 项目 | 原R06（r03内） | r02 | r04 |
|---|---|---|---|
| K1阶段宽度 | 256 | 128 | 256 |
| K0/MMAD顺序 | 64 | 64 | 64 |
| B阶段数 | ceil(K/256) | ceil(K/128) | ceil(K/256) |
| 首次A加载 | 随K阶段流水加载 | 每个M块先完整预载A | 随原K阶段流水加载 |
| 跨N的A复用 | 无 | 全部K | 前512个K元素 |
| L1申请 | 384 KiB | 384..504 KiB | 512 KiB |
| 网格、消费者、最终求和 | 原版 | 原版 | 原版 |

1. **B字节数不变，不代表搬运成本不变。** r02的K1从256降至128，K=1024时B阶段从4变8，K=1504时从6变12；B描述符、相关阶段Set/Wait及标量循环次数增加。之前只强调字节量减少，低估了这项代价。
2. **完整A驻留增加启动依赖。** r02在每个M宏块进入Macro前先执行整段LoadA并等待，随后才加载B并发起MMAD。原版只需首个K1切片即可开始。预载量从约64 KiB增至256..376 KiB（完整128行时）。
3. **节省的不是全部输入。** AM128/BN256时，A每阶段字节量只有B的一半。A可能受缓存命中影响；减少逻辑GM请求量不保证等比例减少外存流量或总耗时。此处缓存影响尚未实测。

这些事实足以解释为什么“完整A加载次数更少”仍可能更慢；但没有精确shape/plan和硬件计数器，不能确定两项代价各占多少，也不能仅凭轻微劣化确定两点均命中新分支。

## r04如何修正

保留原R06的K1=256、K0=64、L0双缓冲和事件协议。在原384 KiB L1配置之外，用剩余128 KiB存放`128×512×2`字节的A前缀：

- A1流式区：两个`128×256`槽，128 KiB。
- A1缓存区：两个`128×256`槽，128 KiB。
- B1双缓冲区：两个`256×256`槽，256 KiB。

每个M宏块的第一个N宏块，按照原流水将前两个A阶段写入缓存槽，K≥512的部分进入普通流式槽。后续N宏块复用前两个缓存槽，仅加载其余A。切换M块或任务时，首个N宏块重新填充缓存，避免混用不同M/batch的数据。

没有单独的LoadA预载，也没有增加A专用事件。原Macro结束时已经排空本宏块的L1/L0读者；继续用这些依赖保护缓存生命周期。N循环顺序、ring槽序、两个AIV所有权、partial和最终求和均保持原版。

分派条件与r02一致：B=1，M/N≥1024、K∈[1024,1536)，满足原R06资格/family，且`floor(nTiles/pN)≥2`。16/32对齐及输入上限继承原R06。已知11/12的K区间不命中；点2命中r03原分支。

对固定plan，A逻辑请求字节量变为：

```text
2 * B * M * [512*pN + (K-512)*nTiles]
```

B请求字节和描述符数量都与原版一致。新分支仍有缓存槽选择和条件分支，L1占满512 KiB；实际效果待测，不保证一定加速。没有复用机会时保留原R06。精确9/10的plan仍未知，若无收益，不继续用字节公式代替性能证据。
