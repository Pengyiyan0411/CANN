# v12_r05：一次确认9/10是否满足r04完整守卫

提交文件：[v12_r05_probe_r04_coverage.asc](v12_r05_probe_r04_coverage.asc)。

这是**诊断版**，命中后故意降低并行度以得到可识别信号。主线仍为[v12_baseline_r03.asc](v12_baseline_r03.asc)，不要将r05作为性能基线。r05直接基于r03，完整保留点2改动；不包含r02/r04的A缓存kernel。

## 本轮只提交这一份

同一份结果同时读取Case9和Case10，并保存完整15点结果。不再分别探精确B/M/N/K。

只有实际通过原R06的dtype、Eligible及family检查后，才读取未经修改的`observed=MakePlan(...)`，判定：

```cpp
B == 1 && M >= 1024 && N >= 1024 &&
K >= 1024 && K < 1536 &&
observed.nTiles / observed.pN >= 2
```

原R06资格同时提供16/32对齐、输入大小及核数等限制。这与r04新分支的完整逻辑相同；不是只测其中一项，也不是读取压力计划之后再判断复用机会。

成立时：

```cpp
p.pM = 1;
p.pN = 1;
p.tasks = p.B;
p.blocks = 1;
```

仍然执行完整原R06计算，workspace按压力计划重新计算。只改直接R06的TryLaunch，不改共享MakePlan，因此不会通过padded路径误改点8。未命中时执行原r03计划，点2继续r03静态K路径。

## 如何判读

| Case9 / Case10各自表现 | 能得出的结论 | 下一步 |
|---|---|---|
| 正确通过，耗时明显接近该点已校准的R06单组压力状态 | 完整守卫HIT，r04会接管该点 | 才能将r04与r03的耗时变化解释为候选实现差异 |
| 保持正常水平，且该点已有可靠的同机制单组阳性校准 | 支持完整守卫NO | 停止在该守卫下调A缓存，后续只区分阻塞条件 |
| 小幅波动，或缺少该点有效单组校准 | 不确定 | 不解码为NO；必要时只补同机制阳性对照 |
| 编译失败、精度失败、TLE | 不能作为谓词结果 | 先处理提交或验证问题 |

Case12曾出现约1.5ms压力信号，**不能把1.5ms作为9/10的固定阈值**；每个点与自身正常状态及自身压力响应比较。若实际只有一个核组，压力计划可能与原plan相同，阴性也不可解码。

这一份只能回答“r04完整守卫是否成立”。NO不能区分B不是1、N分片缺少复用等原因；HIT也不能证明A搬运就是性能瓶颈。本轮先不预付下一层探针。
