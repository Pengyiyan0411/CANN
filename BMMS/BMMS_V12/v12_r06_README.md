## 为什么换方向

r04本次15/15 Pass，Case9为69.09 μs，用户评价收益不明显。它确实命中（r05已有765.68 μs强阳性），所以这次不能再用“可能未命中”解释。结论限定为：这一版部分A缓存没有明确收益，不等价于证明所有搬运优化都无效。

原R06每个128×256宏块在同一个K0切片里执行四个64×128 MMAD。四个输出子块实际复用同一批A/B数据，而现有L0资源已经能够容纳整个128×64的A和64×256的B。因此本版将L0排布改成完整操作数，每个K0阶段执行一个128×256 MMAD。

满宏块K=1024的静态调用量：

| 项目 | r03内原R06 | r06 |
|---|---:|---:|
| MMAD | 64 | 16 |
| B的LoadData调用 | 128 | 64 |
| A的LoadData调用 | 128 | 128 |
| K0切片数 | 16 | 16 |
| A/B的GM→L1描述符 | 各4 | 各4 |
| Fixpipe | 4 | 4 |

减少的是指令调用与相关标量循环，浮点运算数量没有减少。更大的MMAD单条执行更久；不能把调用数缩为1/4解释成耗时缩为1/4。此方案针对指令拆分开销，未获得profiling证明它是唯一瓶颈。

## 数据布局与精度边界

1. A2按完整`ar×kr0`排布，不再按两个64行子块分别排列。
2. B2按完整`kr0×br`排布，不再按两个128列子块分别排列。四种TA/TB都显式处理原L1 NZ源索引。
3. L0C是一张完整`ar×br` NZ矩阵。写回旧ring时仍分原四个子块，源偏移为`(no/16)*ar*16 + mo*16`，Fixpipe的`srcStride=ar`，不能沿用子块高度mr。
4. ring布局、消费者、宏块顺序、pM/pN和workspace全部沿用原R06。先完成K累积，再沿N取Max，最后沿M求和。
5. K1=256、K0=64，L1/L0双缓冲和FP32输出保持。没有重做R31的K0=128加L0单缓冲，也未带入r02/r04的A驻留。

已对照官方[Mmad布局与参数说明](https://www.hiascend.com/document/detail/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0249.html)及[Fixpipe源NZ步长说明](https://www.hiascend.com/document/detail/en/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_0251.html)。文档核对不替代测评环境的实际CANN编译。

L1仍393,216 B，L0A/B/C仍32/64/128 KiB。没有通过越过缓冲区预算、压缩精度或跳过计算换速度。

K切片与累加调用顺序相同，但更大的单条MMAD在真实Cube上的内部数值行为仍需精度验证，不能从CPU模型宣称所有设备位级行为相同。

## 分派范围

保持r05已测试的完整守卫：原R06路径、B1、M/N≥1024、K1024..1504且原对齐限制成立、原`floor(nTiles/pN)>=2`。

最后一项对大块MMAD不是数学必要条件，本版保留它用于隔离已获强阳性的Case9，不同时扩大到Case10未知域。函数名ReusesA沿用旧门槛，但本版没有缓存A。r05对Case10支持NO，预计继续原R06；这仍是基于先前探针的结论，不是当前版本已经实测。
