## 1. 这个分支究竟改了什么

对 `C12R2_NBIT1.asc` 与 `v12_baseline_r41.asc` 做源码差分：除新增 `bmms12opt` 模块和一个 dispatch 入口外，其余代码只有注释、空行和换行格式差异。它的基础仍是 r30 的完整宏块 MMAD producer + 双 AIV row-max consumer。

| 项目 | r41 中 Case12 的 r30 路线 | 队友 O10 路线 |
|---|---|---|
| 宏块 AM×BN | 128×256 | **256×128** |
| K1 / K0 | 256 / 64 | 256 / 64 |
| L0C 单宏块 | 32768 FP32，128 KiB | 相同 |
| 宏块网格，假定 N=4096 | 10×16 | **5×32** |
| pM×pN，20 核 | 10×2 | **5×4** |
| 每核宏块数 | 8 | 8 |
| 每个 AIV 接收的半宏块 | 64 行×256 列 | **128 行×128 列** |
| 行内折叠到 64 lanes | 三次 Max | **一次 Max** |
| 跨 N 分片最终 Max | 2 份 | 4 份 |
| GM ring 大小 | 5 MiB | 相同 |
| row partial 大小 | 10 KiB | 20 KiB |

它保留了 GM→L1 双缓冲、L1→L0 双缓冲、下一个宏块首个 K1 slab 的预取、Fixpipe 发布完整宏块，以及 AIC/AIV ring credit 同步。K 的计算顺序没有重排，也没有 Split-K 求和。

因此收益应理解为**宏块形状、分核比例、操作数搬运及向量归约共同改变**。不能直接断言全部收益来自 B 带宽，更不能把它当成只改 planner 的实验。

### 入口边界

合并保留原分支的有效入口：

```text
B = 1, M = 1280, K = 1536
4096 <= N < 6144, N % 64 = 0
dtype = BF16, TA = true, TB = false, cores = 20
并满足原 R06 eligibility / family 检查
```

入口放在 r41 与 r30 之间；r72 的小点入口仍在前面。r2 移除新增模块和入口后，可以逐字节还原 r1。这一校验比仅凭某次小点计时接近更直接地证明了代码合并边界。

### NBIT1 必须删除

原文件实际包含：

```cpp
const int qN = (N - 4096) / 64;
if (((qN >> 1) & 1) != 0) {
    p.pM = 1; p.pN = 1; p.tasks = B; p.blocks = 1;
}
```

它是通过降低并行度制造毫秒级信号的诊断代码。直接提交它，会使入口内一半的 N 候选被故意降速。r2 仅删除这段诊断逻辑，保留 O10 producer、consumer、guard 和 planner。

## 2. Case12 形状：推导成立的条件与证据强度

**按新总结所报告的完整五位结果**，工作画像为：

```text
B=1, M=1280, N=4096, K=1536
BF16, TA=true, TB=false, 20 AIC + 40 AIV
物理 A: [1,1536,1280]，物理 B: [1,1536,4096]
输出: [1] FP32
```

逻辑证明：入口限制 N∈[4096,6144)，且 `AlignedPitch` 在 TB=false 时要求 **N%64=0**。所以 q=(N−4096)/64 是 0～31 的整数；若五个独立、已校准的 q bit 探针都读零，q 必为 0，N=4096。这里没有把 `/64` 的向下取整误当精确除法。

不过，本次实际拿到源码的只有 **NBIT1**；另外四位的谓词与校准结果来自队友总结。单独 NBIT1 正常只能确定 q 的 bit1 为零，**不能独立证明 N=4096**。M、K、dtype、layout 的冻结事实以及线上命中 kernel 的证据同样来自所给总结；入口本身不能代替命中证明。

本地的性能复测没有在 N=4096 上复现总结中的明显加速，而 N=4160、6080 的收益较大。这个现象**不能单凭耗时反推真实 N**，也不能推翻用户确认的线上收益；它提示我们暂时保留原入口范围，不急于把提交锁死为 N=4096。详细数字见 `VALIDATION.md`。

## 3. 搬运模型：哪些解释有依据，哪些不能直接下结论

假定上述精确形状，BF16 原始 A 为 3.75 MiB，B 为 12 MiB。按当前源码每个宏块重新读取完整 K 的两侧输入：

| 路线 | A 的 GM→L1 请求量 | B 的 GM→L1 请求量 | 合计 |
|---|---:|---:|---:|
| 128×256 | 16×3.75 = 60 MiB | 10×12 = 120 MiB | 180 MiB |
| 256×128 | 32×3.75 = 120 MiB | 5×12 = 60 MiB | 180 MiB |

**总请求量没变，是 A/B 的比例调换了。** 这些是代码层的重复搬运请求量，不是实测 HBM 流量；L2 命中、Nd2Nz 布局转换、指令发射和各流水段重叠都会影响真实耗时。

总结中的 A_LOAD_X2 +22.85 μs、B_LOAD_X2 +20.04 μs、RINGREAD_X2 +3.78 μs，支持优先研究操作数供给。它们并不等于原运行中各阶段独占的耗时。重复同址读取也会改变缓存状态和重叠关系，故 `Δtime/MiB` 不能直接当成稳定带宽，更不能据此证明 O10 已经是全局最优比例。

## 4. 更有效的下一步顺序

1. **先用本次 r2 做 Judge 15 点回归。** 这是 r72 小点改进与线上获益 Case12 路线的干净合并。确认实际命中并保存完整提交哈希、15 点耗时；不再把探针版当性能基线。
2. **解决本地代理与线上收益不一致的问题。** 优先复核现成 NBIT0 源码/校准、实际编译选项、输入布局和测时/缓存条件，而非马上追加一大包 shape 探针。不要依据本地某个 N 恰好提速，就把它认定为隐藏 shape。
3. **分层定位 feeding。** 固定 O10，分别测试 L1→L0A、L1→L0B 的额外 LoadData，以及关闭 next-macro prefetch。用串行 A/B/B/A 与原版比较。重复读实验只作敏感性辅助；优先结合 profiler 的 MTE1/MTE2/M/MMAD 空闲和重叠判断关键路径。必要时补 Fixpipe 对照，ring/reduction 排在后面。
4. **若 MTE1/发射开销占主导，先减少 LoadData 的循环与参数计算。** 当前每个 K0，A 使用 16 次 LoadData、B 使用 4 次；确认可表达相同 NZ 布局后再比较更紧凑的加载描述。精确 metadata 特化可同时消除尾块、kCount、分片边界计算，但应作为独立版本测量，不能预先承诺两位数收益。
5. **若 MTE2/Nd2Nz 主导，再考虑驻留复用。** 例如 AM128 的完整 A 面板占 384 KiB，加 BN128 的双缓冲 B256 slab 占 128 KiB，恰好填满 512 KiB L1；它能减少 A 重载，却会增加 B 重载并失去资源余量，必须独立验证，不能仅算总字节就宣布获益。

资源约束对下一步非常关键：O10 的双缓冲 L1 已用 384 KiB，L0A **64 KiB 已满**、L0B 32 KiB、L0C **128 KiB 已满**。在当前缓冲结构下，把 K0 从 64 加到 128 会让 L0A 翻倍越界；把 K1 直接加到 384 会让 L1 达到 576 KiB。不能继续不受资源约束地放大 tile。AM320/BN96 既增加 A 请求量又触及 L0A 限制，不应作为下一主线。

## 5. 验证口径

沿用现有比赛单 ASC / C ABI 验证工程，不为合并改造成 PyTorch 扩展。CPU FP64 标杆计算的是实际量化输入的 `sum_M(max_N(A@B))`，输出为 FP32；严格阈值保持 `1e-4 + 1e-4*abs(reference)`。性能使用实际 NPU 上的旧版/新版配对 msprof task duration，排除前若干次预热，不使用带分配、同步和 D2H 的 host wall time。

测试用例为针对源码入口自行设计，覆盖全部 32 个 N%64 候选、负值尾块、零、尺度变化、相同列、M/K 抵消、layout/dtype/shape 入口失配以及小点回归。它们是本地合成输入，不等于比赛隐藏的 15 个输入。

精度异常、工具报告以及本地/线上差异均在 `VALIDATION.md` 中单独记录，不用“进程返回 0”代替内存/同步检测通过结论。
