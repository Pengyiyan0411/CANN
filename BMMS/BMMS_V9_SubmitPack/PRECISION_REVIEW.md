## 实际存储值与 oracle

FP16 先转换到实际 NumPy FP16 储值。BF16 先执行 RNE 的 16 位编码，再解码成 FP32 容器；oracle 和模型读取同一批已量化值。另检查 BF16 正负 midpoint 的 ties-to-even，不能用尚未量化的 FP32 随机数充当 BF16 golden 输入。

Oracle 按 batch/M/N 分块，每个 dot 的 K 完整使用 FP64，行最大值始终保留 FP64，最后按 M 求和后只转换一次 FP32。它没有使用 PyTorch FP32 dot 作为参考，也没有在每行 dot 完成后强制舍入 FP32。测试检查输入字节未被修改。

四布局验证独立使用 flat 公式：A 的 batch 基址 `b*M*K`，元素偏移 `m*K+k` 或 `k*M+m`；B 的基址 `b*K*N`，偏移 `k*N+n` 或 `n*K+k`。范围检查与物理布局复原覆盖所有普通场景。NN/TN/TT 的数学场景不意味着 S 分支接管这些布局：S 目前只接管 NT。

## D 片段审查

当前 D 限定 M、N 至少 16 且均为 16 的倍数，K≥256 且 K%32=0；其他 shape 留在原路由。实际实现默认 KB128，保留 KB64 编译选项。`pN=min(nTiles,ceil(cores/(B*pM)))` 只补 B/M 分配后的空间占用缺口；不能再把当前实现描述为固定 pN=1。

- Producer 的 `task → AM256 → BN512 → mo64 → no128` 顺序与所复用 P01 `SmallKConsumer` 一致。每个 tile 的首个 K stage 设置 `cmatrixInitVal=true`，其余 stage 累加，最后才 Fixpipe；K288 的最后 32 项没有遗漏。
- 四种源地址均带正确 batch 基址与 k0 偏移。ND2NZ/LoadData 的实际设备矩阵布局仍须依靠父任务的源提取模拟及平台编译/运行共同检查；本 Python 脚本只检查 flat 地址公式。
- 当前对齐门保证 `mr/2` 为 8 的倍数，两个 AIV 各自覆盖相邻半行区。没有擅自扩展到奇数 M；若未来放开 M%16，原 `mr/2` 逻辑必须重写。
- N 尾仍是 16 的倍数。consumer 先用 −Inf 初始化，只拷真实 nr 项，避免全负时无效列 0 获胜。按真实 M 写 partial，最终不含 M padding。
- KB128 显式 producer 资源：L1 98,304 B，L0A 32,768 B，L0B 65,536 B，L0C 32,768 B。KB64 分别为 49,152/16,384/32,768/32,768 B。KB128 的 L0B 正好达到 64 KiB，不能再同时放入其他 L0B buffer。复用 consumer 的显式 UB 合计 132,256 B，上界低于 192 KiB；这些不包含尚未确认的编译器/API 隐含资源。
- pN>1 时 partial 的实际布局为 `[B,pN,M]`；每个 N shard 完整覆盖其 M 行，每条 `(b,ns,m)` 只写一次。所有 shard 的逐行 Max 合并完毕后才 Sum(M)，未将每个 N shard 缩成标量。
- 两槽局部事件在静态计数模型中各产生和消费一次；最终清空实际发布槽。该计数不能证明硬件 flag、两个 AIV 的 mode 0x2 收齐语义、cache 可见性或死锁自由。禁止把 Python 标量 credit 模型称作硬件同步测试。

D 的已知强反例补零到 K256 后落在实际新路径域：B1,M8192,N16,K256；A 偶数行 `[1,2^-12]`、奇数行 `[-1,0]`；B 每列 `[1,2^-13]`，其余 K 为 0。golden=2^-13，单 FP32 C 后输出 0，严格与组合容差都失败。脚本用两行小矩阵加精确重复计数复现，避免构造大 C。

## S 片段审查

当前 S 限 NT、M2..32、N2..64、默认 MN≤256、K1024..8192，K%8=0，且 Cube 空间分块数小于可用核数。MN2048 是显式实验扩域选项，不应与默认覆盖混淆。

任务编号 `(((b*M+m)*N+n)*splits+ks)` 与最终 `first=(m*N+n)*splits*8` 的读取布局匹配。每个任务独占 32 B 记录，K 按 8 项量子划分，无空段；每 batch 合并固定按 m、n、ks 顺序读取。先合齐全部 K 的 dot pair，再 Max(N)，再 Sum(M)，没有把 K 局部最大值当作完整最大值。

输入缓冲先清零，DataCopyPad 只读有效 K，显式将不足 16 项的尾补零，256 项树的其余 lane 保持零。K 段可能从 8 项、即 16 字节边界开始；真实 DataCopyPad 的源地址支持与 padding 行为仍需平台确认，CPU memcpy 模型不能认证它。

Python 数值模型匹配源码关键顺序：每个 256 项块的二叉树折半到 8 对，然后这 8 对**直接加入 task pair**，没有先构成一个不同舍入顺序的 block pair。跨 K shard 再按固定顺序合并；规范化 pair 按 high 再 low 比较，选中的两个分量都参与最终 M Sum。

显式 UB 为 `5664 + MN*splits*32` B；默认上界 13,856 B，扩域上界 71,200 B。父任务/实现任务另做真实源码规划器枚举，本报告不把其结果计入上述 224 个 Python 场景。

跨 PIPE_V/PIPE_S 的标量读取和 Scalar SetValue 需要完整依赖。审查过程中另一个实现任务发现 VECOUT 队列 `AllocTensor` 后、Scalar `SetValue` 前缺 V→S fence，片段所有者已补两处；本次冻结前已读源码确认记录缓冲与最终输出两处均包含修复。这类缺陷不可能被纯 NumPy 模型捕捉。

### S 修复了哪些例子

B1,M2,N2,K1024，A 第一行 `[64,2^-6]`，第二行 `[-64,0]`；B 每列 `[64,2^-7]`，其余 K 补零。单 FP32 C 会输出 0，而 pair 贯穿 Max/Sum 的模型得到正确 2^-13。

另外将低位放在 K4104 的末项，两列低位分别为 2^-13、2^-12，按 4 个 K shard 合并；模型正确选择 high 相同而 low 较大的列，消减后返回 2^-12。两个例子均覆盖 FP16/BF16。

### S 尚未修复的确定性反例

**两分量低位再次舍入**：B1,M32,N2,K1024；A 的每行前 5 项为 `[32768,8,2^-9,-32768,-8]`，B 的每列前 5 项为 `[32768,8,2^-9,32768,8]`，其余为 0。全部数可由 FP16 和 BF16 精确表示。

每条 dot 的 FP64 值为 2^-18，golden=32×2^-18=2^-13=0.0001220703125。当前 pair 模型输出 0。标量合并到 `hi=2^30,lo=64` 时，新残差 2^-18 恰为 low 的半 ULP，`lo+e` ties-to-even 舍回 64；随后两个大项消减，已丢残差无法恢复。严格和组合门均失败。这是“hi/lo 已保留到最后”仍不足以证明全域精度的具体例子。

**有限 BF16 乘积先溢出，但 golden 有限**：B1,M2,N2,K1024；A 两行 k0=k1=2^64，B 每列 k0=2^64、k1=−2^64，其余为 0。完整 FP64 dot 与输出均为 0；FP32 Mul 得到 ±Inf，后续 TwoSum 产生 NaN。它与“golden 最后自己转成 Inf”的题面缺口不同，不能用有限输入假设排除。
