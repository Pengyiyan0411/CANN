# BMMS 性能停滞复盘与突破路线

2026-10-01。当前已接受基线仍为 `BMMS_V12/v12_baseline_r41.asc`；本次复核源码、历史实验、平台配置和官方参考，没有运行新的 NPU 实验，也没有生成或晋升提交版本。

## 判断

尚无证据表明已经接近硬件极限。更明确的问题是：近期在同一计算方向、同一宏块同步方式内反复优化输入复用，同时为复用改变分核和归约；实验同时付出了别的代价，难以把结果推广到未知的隐藏点。

有三条值得补齐的路线：**独立 FP32 输出 GEMM 对照、UnitFlag 细粒度计算/搬出交叠、转置乘积 D=BᵀAᵀ 的等价计算方向**。后两项在旧设计里有过提及，但当前主线与近期候选未见启用 UnitFlag；本次归档检索也未找到转置乘积的上卡结果。不能把“写过设计”当成“已验证无效”。

这不等于已证明某个开关可以追回 Case12 的全部差距。

## 2. “少读B”为什么没有自然换来加速

[实际平台配置](V12_npu_lab/results/case12_wide_load_20261001/evidence/r62_platform_config.log)列出L2大小176,160,768字节，即168MiB。

以本地实测配置M1280、N5120、K1536、两字节输入为例：

- A = 3.75MiB，B = 15MiB。
- 原20核两槽FP32宏块环区约5MiB。
- A+B+环区约23.75MiB。
- 完整FP32 C为25MiB；A+B+C约43.75MiB。
- 每个C元素一次写GM、一次读UB，逻辑中转量约50MiB。

这些量低于配置列出的L2容量。**重复GM请求有可能由L2服务，不能把逻辑B读量直接当成HBM流量。** 尚未测到命中率，L2也可能共享/受分区及冲突影响，不能反过来保证全部命中。

因此，B驻留方案节省的可能主要是L2→L1搬运；它额外引入的L1→L0搬运、细块计算、Scalar控制和归约足以抵消收益。纸面逻辑B读量下降80%以上，并不意味着总时间也有对应下降。

## 3. 第一项缺失实验：建立真正独立的GEMM标尺

r41对r59/r63的对照只能判断谁更快，不能判断整个手写Cube主循环是否优秀。目前没有找到同一批Case12合成输入、FP32 C语义一致的成熟GEMM性能对照。

应在同卡同shape/layout/dtype上比较：

1. r41完整BMMS。
2. 抽取现有生产者形成纯GEMM、输出完整FP32 C。
3. 一个固定版本CATLASS或本机可用Matmul的纯GEMM，输出同样FP32 C。
4. 独立rowmax+sum，以及第3项接该归约后的完整两阶段BMMS。

第2项与第3项的差距诊断矩阵乘主体；第4项完整结果与第1项比较才判断融合是否值得。不能简单将两个独立profile时间相减，作为原融合流水内的排他开销。

**单kernel不自动更快。** 现有融合路径仍有C的GM中转，它省峰值空间并允许交叠，但也引入环区信用和共同调度。成熟GEMM+归约即使多一次launch，也可能提供更好的基准；这是一项待验证假设，不是建议直接改成两kernel提交。

对照必须保留真实FP16/BF16输入和FP32 C；普通半精度输出GEMM再cast成FP32不是同精度对照。外部库可作为离线标尺，最终提交仍需满足当前单文件/ABI约束。

## 4. 最先值得落地的硬件特性：UnitFlag

当前[Case12生产者](BMMS_V12/v12_baseline_r41.asc)的关键位置：

- 第5665行：复用L0C前等待FIX_M。
- 第5669行：MmadParams未设置unitFlag，默认0。
- 第5687–5688行：整块M_FIX事件交接。
- 第5693–5696行：完整宏块Fixpipe，然后发布FIX_M。

这形成了明确的整块MMAD/FIX依赖。L0C为单个128KiB，不能直接再加一个同尺寸buffer。

官方[CATLASS策略文档](https://catlass.readthedocs.io/zh-cn/latest/2_Design/01_kernel_design/03_dispatch_policies/)将UnitFlag用于MMAD与搬出细粒度并行。[本地固定源码](V9_design/references/catlass/include/catlass/gemm/block/block_mmad_pingpong.hpp)第294行附近对累加中的MMAD使用保持标志，末次使用释放标志，配套Fixpipe；非UnitFlag分支才使用整块M_FIX/FIX_M交接。本机归档CANN9头文件包含该参数，dav_c220实现将其传给底层mad指令。

建议先做独立协议实验，保持r30的宏块尺寸、K顺序、分核、GM两槽和消费者不变，只替换L0C计算/搬出交接：

- 验证多次K累加、多个连续宏块、环区回绕和尾宏块。
- 必须等完整K结果满足搬出条件，不能每个K64片段都提前发布C。
- GM READY仍由实际FIX完成保证；GM FREE仍由AIV读完保证。
- 不照搬其它芯片API，不把旧版文档关于累加的简化描述当作当前协议证明；依目标CANN、官方对应代码和实卡验证共同确认。
- A/B加载、原partial结构不改，避免再次混入归因不清的改动。

这是低改动量、可单独证伪的优先实验。现有FIX活动约8–10μs只提供收益量级线索，不能将其全部扣除，更不能承诺仅此把114μs降到85μs。

## 5. 最值得做的结构性备选：直接计算转置乘积

数学等价式：

```
C[m,n] = sum_k A[m,k] B[k,n]
D[n,m] = sum_k B[k,n] A[m,k] = C[m,n]
Y      = sum_m max_n D[n,m]
```

只改变计算方向，仍完整K点积，然后对原N求max，最后对原M求sum。输入指针交换后，逻辑维度M/N交换，转置标志为 TA'=!TB、TB'=!TA。可直接解释原物理输入，不要求另做全矩阵转置。

为避免重蹈“换方向同时换分核”的问题，首个实验固定原始输出所有权：

|项目|原路径|转置乘积实验|
|---|---|---|
|原C覆盖范围|原M128×原N256|相同|
|硬件MMAD的M×N|128×256|256×128|
|K0/K1|64/256|相同|
|L1双缓冲总量|384KiB|384KiB|
|L0A双缓冲|32KiB|64KiB|
|L0B双缓冲|64KiB|32KiB|
|FP32 L0C|128KiB|128KiB|
|最终partial归属|原pM/pN计划|保持相同|

平台配置的L1→L0A/B速率项分别为512/256，A/B搬运布局也不同；交换操作数角色有机会改变负载分配。但这些配置项不能直接换算成加速倍数。

AIV应读取D的原M列片，沿D第一维即原N作max，不能调用旧row-max后直接求和。两AIV可继续各自负责原M的64行对应结果，保留最终2份partial，不引入20份partial的新合并代价。

与r53的M256×N128不同：r53仍计算原C，改变了原矩阵覆盖几何；本方案计算D，首测保持原C的覆盖几何不变。二者不能互相替代为实验结论。

旧V8方案第13.3节提过该恒等式，尚未找到实际设备验证。其收益风险是列向归约、转置装载及MMAD内部时序，需要独立精度和性能验收。

## 6. 访存冲突方向：先改N遍历，再考虑Shuffle-K

[CATLASS优化指南](https://catlass.readthedocs.io/en/latest/1_Practice/11_matmul_optimization/)把预取、swizzle、shuffle-K分别作为调节项；Shuffle-K用于错开访问地址、缓解bank冲突。

本地N4096→4160只增加1.56%的有效乘加量，但原r41时延可增加约28%。不过nTiles也由16→17，最忙核宏块数可能由8→9，因此不能把跳变全部归因于stride或bank冲突。

最低成本对照应保持pM/pN、各核任务集合、K累加顺序、输出归约不变，只改变每个N-shard内的宏块遍历相位/顺序，检查MTE2和完整时间。分别覆盖相同nTiles但不同pitch的输入，区分负载量化和地址冲突。

Shuffle-K改变浮点加法顺序，先核对数值契约并重新做强相消测试；不把它当成无风险开关。本轮不优先修改K顺序。

## 7. 实验选择方法也要修正

“不让所有形状都退化”适合评价全域替换，不适合否定所有局部专用路线。近期首筛8个形状混合了输入受限与计算/流水受限两类。

今后先用探索样本提出基于公开metadata的适用域，再冻结guard，用独立M/N/TA/dtype样本检验域内收益与域外回退。探索数据不得同时充当最后留出证明。已有r60/r63局部赢家继续作为研究证据，不直接晋升。

隐藏Case12的TA/dtype/精确N及Judge核数仍不能从约114μs反推。r58已有校准诊断可以补最关键入口信息；不必恢复每一位shape后才做通用实验，也不能假装真实目标已经完全确定。

## 8. “卡分”与“Case12卡时延”需要分开看

按[历史榜单复核](BMMS_V12_榜单收益与优化优先级_20260928.md)已验证的公式：

```
总分 = mean_i(100 / (1 + ln(t_i/T_i)/ln(1.5)))
```

它不是几何平均加速比。以[最新已归档完整15点截图](V12_results/2026-10-01_r55_feedback/RESULTS.json)的同一组参考时间固定复算，约43.5748分；这是计算结果，不是新平台成绩。本轮网站正文读取失败，没有更新实时排行榜。

下表只是假设该点时间下降10%、其它点及参考不变的分数敏感度，不是预计收益。

研发顺序建议：**同精度GEMM标尺 → 原r30上的UnitFlag单变量 → 转置乘积 → 有机制证据再做N遍历/冲突调整**。有效的低层改进再分别验证9/10/11，不直接扩大接管范围。

为总分分配精力时，同时保留Case15的小幅补分，以及Case6、3/4的独立结构路线。Case6需最少路由确认后才能可靠开发。暂停继续给Case12的B驻留增加缓存或微调merge。
