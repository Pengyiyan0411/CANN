2026-09-28。结论：点2当前最有用的工作画像是 **单 batch、M/N 都在2到16之间、K在32到128之间且8对齐**。这来自用户提供的诊断报告，尚未找到对应原始 Universal 探针源码与逐次成绩，因此不升级成独立复核过的精确 shape。R50 覆盖其中的 Tiny/Resident 子集，以输入元数据分派。

## 2. 修正报告里的路线简化

报告把该范围全部归到 Tiny/Resident，但源码还有工作量门槛。

```cpp
UseTiny = M*N <= 16 && K <= 1024 && M*N*K <= 8192;
UseResident = M<=32 && N<=64 && K<=128 && M*N<=256
           && M*N*K<=16384 && (M+N)*K<=8192;
```

在上述点2工作集合内，分类进一步化简为：

| 子域 | 原路线 |
|---|---|
| `M*N<=16` | Tiny |
| `M*N>16 && M*N*K<=16384` | Resident |
| `M*N*K>16384` | 不满足 Tiny/Resident，需要继续原后续分派 |

例如 `M=N=16,K=128` 的工作量32768，属于 Native 候选；`M=N=15,K=80` 的工作量18000，也不属于 Resident，进入后续通用分派。R50 保留这些例外的原代码，不用未经复核的报告强行扩大接管范围。

## 4. 为什么本轮采用向量分阶段执行

若点2属于 Tiny/Resident，原实现 B=1 时只有一个 AIV：没有可以通过增加 batch 并行利用的第二个 batch。原代码已经不需要 GM partial 或跨核汇总，不能将取消这些机制作为本轮优化理由。

源码显示原计算按 M 逐行推进，反复组织 gather、乘法、点积求和、行最大值与同步。R50 将不同点积的中间乘积保留在 UB，把独立工作集中到几个阶段。其代价是更大的 UB 占用，潜在收益是减少串行阶段和行间同步；是否成为真实收益只能由板上结果确定。

保留两套原始求和结构：Tiny 的 `ReduceSum(K)` 与 Resident 的128→64折叠加 `WholeReduceSum`。这样避免把性能实验与数值算法切换混在一起。支持全部四种布局和两种输入精度。

全部目标域的 UB 公式枚举峰值146,560字节；不依赖 exact M/N。新策略的接管条件严格限制在单 batch 的目标子域，原策略保持可回退。
