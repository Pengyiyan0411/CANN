## 2. 算子目标、约束与正确性边界

算子计算：

```text
C[b,m,n] = Σk A[b,m,k] × B[b,k,n]
y[b]     = Σm max_n C[b,m,n]
```

输入为 FP16/BF16，输出为 FP32；支持 TA/TB 四种转置组合。当前接口约束为 `1≤B≤64`、`1≤M,N≤8192`、`32≤K≤8192`、`K%8=0`，且 `B*M*K`、`B*N*K` 各不超过 `2^26`。`cores` 指入口传给 planner 的有效核数，不是通过截图测得的硬件利用率。

正确性要求贯穿所有优化：

- K 分片必须先相加得到完整 C，再做 N 维最大值；不能对各 K 分片先取 max 后相加。
- N 分片产生的是行最大值的局部结果，需要先跨 N 取 max，再跨 M 求和。
- 参考计算以实际量化后的输入为基础，执行高精度点积、max、sum 后得到 FP32 输出；不能拿量化前的随机数当参考。
- 交付为完整单个 `.asc` 文件，保持 `run_kernel` ABI 及官方主程序/构建约定。不同版本不能拼接使用。

接口与初始设计见 [V11 DESIGN](V11_impl/DESIGN.md)、[测试约束](V11_impl/TESTCASES.md)。历史数值审查仍保留 3 项极端输入限制，涉及 FP32 抵消误差、BF16 相关中间溢出等，尚无本轮修复证据；见 [精度审查](V9_impl/precision_review.md)。15 个平台点全部 Pass 和显示误差 0.00%，都不构成全输入数值域正确性证明。

## 4. 当前 R25 的执行架构

### 4.1 分派顺序

从 [冻结 R25 源码](BMMS_V11_R25/R25_NATIVE_TARGETED.asc) 的 `run_kernel` 看，实际入口依次为：

```text
输入元数据校验，得到 B/M/N/K、dtype、TA/TB、cores
  → bmms11r2::TryLaunch       Macro dense
  → bmms23::TryLaunch         小输出 long-K Split-K
  → bmms11d::TryLaunch        R03 residual dense
  → bmms8::Classify
      → Tree                 部分连续 skinny family
      → Native fixed-small-K
          → bmms25::TryLaunch
          → 原 Native
      → 原 V8 fallback
```

所有生产策略都根据合法输入元数据分派，Case 编号只是报告中的实验标识，不进入运行时判断。`semantic family` 与实际 kernel 路线不同；例如 Case15 的 family 是 `SmallOutput_LargeK`，当前实际先进入 Split-K，不能继续按“走 R03”描述当前执行。

历史讨论中“R06 条件”常指 Macro eligibility；这里以实际 `bmms11r2::Eligible` 为准，避免与独立实验文件 `R06_MACRO_MMAD` 混淆。

### 4.2 主要路线及限制

| 路线 | 主要适用条件 | 当前实现要点 |
|---|---|---|
| Macro | M≥128、N≥256、K≥256；M/N 16 对齐，K 32 对齐；宏任务数足够覆盖 cores；排除 Tiny/Resident | 64×128 基础输出块，128×256 宏块；K1=256 双 L1、K0=64 双 L0；宏包发布和消费 |
| R03 residual | M/N≥16 且 16 对齐；256≤K≤8192 且 K%32=0；不满足 Macro，排除 Tiny/Resident | 64×128 输出块，K128 分段累加；通过 B/M/N 提供空间任务 |
| Native | M/N≥16 且 16 对齐；K∈{32,64,128}；排除 Tiny/Resident | 64×128 输出块，256×512 宏观输入分区；全 K 计算及 4 tile 输出包 |
| R23 Split-K | 16≤M<128、16≤N<256，均 16 对齐；4096≤K≤8192 且 K%32=0；空间任务不足时分片数至少 2 | K 分为 2/4/8/16 片；各自产生 C partial，再先跨 K 合并、后 max/sum；不用原子累加 |
| R25 small | 原 Native，K128、B>1、M/N≤32、原 blocks>1 | 单个 batch 的小输出由一个 AIV 完成 max/sum 并直接输出，避开局部结果的全局合并屏障 |
| R25 dense | 原 Native，K128、B=1、M/N>32、原 blocks>1 | 汇集 N 局部结果，2D DMA 与 tree max；保留完整 M ReduceSum 及相应合并同步 |

以上是条件摘要，不取代源码中的全部 dtype、范围、资源检查。FP16/BF16 和四种转置仍由相应模板分支处理。

形状 guard 能限定改动的输入集合，**不能保证只影响某个编号的测试点**。多个未知测试点可能共享同一范围；即使未命中路径的 host 启动记录完全相同，也仍不能直接保证实际二进制性能完全相同。

### 5.1 Case5/13/14：N01–N05

这批探针只在实际 Native 分支中、条件为真时执行同一种 one-group stress。五次均有完整截图，15/15 Pass，用户明确按 N01–N05 顺序标注。

| 探针 | 条件 | Case5（μs） | Case13（μs） | Case14（μs） |
|---|---|---:|---:|---:|
| N01 | K==32 | 7.49 | 17.15 | 14.56 |
| N02 | K==64 | 7.84 | 17.56 | 15.13 |
| N03 | M≤32 | 14.67 | 17.51 | 14.96 |
| N04 | N≤32 | 14.60 | 17.83 | 15.15 |
| N05 | B==1 | 7.58 | 98.42 | 43.23 |

Case5 的 M/N 条件均有强响应，B==1 无响应；13/14 的 B==1 有强响应，M/N≤32 无响应。三点在这批中各有有效阳性压力信号，因此结合 Native 固定 K 集合和 K32/K64 两个阴性，可支持三点均为 K128。

分类上需要特别纠正：**Case5 的 M 和 N 同时≤32，因此并不是 ShortM 或 ShortN，而是 Dense_SmallK。** ShortM 要求 `M≤32 && N>32`，ShortN 要求 `N≤32 && M>32`。13/14 的两维均>32，也属于 Dense_SmallK，但与 Case5 在 batch 和输出大小上是两类结构。

13 的压力耗时大于 14，不能直接推出 `M13>M14` 或某个精确 M/N；输入搬运、输出面积、计划分片和布局都可能影响压力倍率。证据：[Native 探针审计](V11_results/2026-09-27_d24_native/AUDIT.md)。

### 5.2 Case7：C01 + R7_01–05

| 探针 | 仅在实际 R03 中检查的条件 | Case7（μs） | 判断 |
|---|---|---:|---|
| C01_R03_1G | 无条件压为单组 | 32.79 | 阳性对照成立 |
| R7_01 | M<128 | 33.58 | HIT |
| R7_02 | N<256 | 33.09 | HIT |
| R7_03 | B·ceil(M/128)·ceil(N/256)<cores | 34.30 | HIT |
| R7_04 | K≥512 | 11.44 | NO HIT |
| R7_05 | K≥1024 | 11.45 | NO HIT，与上一项一致 |

因此 K 可收窄到 `{256,288,320,352,384,416,448,480}`。M<128、N<256 令 R7_03 两个 ceil 均为 1，所以进一步得到 `B<cores`。Macro 的 M 下界、N 下界和宏占用条件，在此点上均未满足。

原 R03 使用 64×128 tile，mTiles/nTiles 各为 1 或 2，故原 `B≤tasks≤4B`，`blocks=min(cores,tasks)`。压力探针同时改变 pM/pN 和 blocks，但仍依次处理 B 个 batch；它证明计划对并行调度敏感，**不能单独判断收益来自 batch 并行还是 M/N 分片**。不能因此推出 B=1、M>64、N>128，或精确核组数。

旧 C512 旁路的正常→fallback 差距只有约 11→13 μs，阴性不足以推出 K<512。本次 K 上界来自约 11→33 μs 的有效单组压力对照，是新的证据，不能倒过来恢复旧推断。Case7 也不能直接照搬 Case15 的 very-long-K Split-K。证据：[R7 审计](V11_results/2026-09-27_d24_r7/AUDIT.md)。

### 5.3 Case15：从 long-K 到明确的小输出单空间任务

## 7. R29–R31 的失败说明了什么

三个版本各自从完整 R25 出发，彼此不叠加，也没有合入 R26/R27/R28。实现和当时的资源核算保留在 [三路设计文档](BMMS_V11_R29_R30_R31/DESIGN.md)。以下将确定事实与待验证解释分开。

### 7.1 R29：减少短 K 加载调用，没有转化为性能收益

作用域为原 R03 residual，且 `M<128、N<256、K<512、B<cores`，直接覆盖 Case7 已确认的范围。改动是让每个输出块的完整 K 一次进入 L1，保留原 K128 的 L0/累加顺序。

合成示例 `B=1,M=112,N=240,K=480,cores=4` 中，ND2NZ 调用 32→8，MMAD 仍为 16 次，逻辑输入搬运字节仍为 675840。**调用次数减少并没有减少该示例的输入字节或计算工作量。** 用户实测无收益，应以实测为准，R29 不晋升。

可能的解释是加载调用设置不是主要瓶颈，较大的加载增加首个 MMAD 的等待，或者输出消费/同步限制仍在。这些都没有 profiler 证据，不能选一个写成根因，也不能据此说 Case7 已到硬件极限。

### 7.2 R30：增大 M tile 同时改变并行和资源压力

作用域为原 Native，`K=128、B=1、M≥128、N>32、原 blocks>1`。M tile 从 64 改为 128，输出包由 4 个 64×128 tile 改为 2 个 128×128 tile，包字节不变；消费端随之调整。

合成示例 `B=1,M=384,N=528,K=128,cores=8` 中，MMAD/Fixpipe 30→15，但逻辑 GM 字节仍为 897024。大 tile 还可能减少任务数、改变 pM/pN，或者提高 L0/UB 压力。更少 MMAD 不能直接当作更快的依据。

用户现在反馈其他点退化，R30 不晋升。**13/14 的 M≥128 从未被确认**，所以之前或现在没有目标收益，都不能自动解释成“条件没命中”。退化点可能共享同一元数据范围；无逐点数据和设备分析时，不能确定是哪个范围、哪个资源造成退化。

### 7.3 R31：减少 MMAD 的代价是放弃双 L0 重叠

作用域是整个原 Macro 集合，不只 Case10/11。K1=256 双 L1 不变，K0 从 64 改为 128；为控制 L0B 容量，L0 由双槽改为单槽，每段需要等待相应 M→MTE1 复用条件。

整 K 块的 MMAD 次数可减少，但 K 尾部并非总是精确减半，例如 K288 的分段数是 5→3。输入字节没有因此减少。L0 搬运与计算的重叠能力变化，是这次实验的重要代价。

用户反馈其他点退化，R31 不晋升。单 L0 导致重叠变差是合理的待验证解释，**不是已经测定的根因**。回到 R25 的 K0=64 双 L0，不继续仅凭指令计数盲目扩大 K0。

### 7.4 对后续方法的修正

- 把“少调用/少指令/少中间数据”降为待测试的假设，不再把模型计数称为已经实现的加速。
- 必须同时核对每次改动对计算块、独立任务数、启动波次、缓冲容量和重叠的影响。
- 按元数据设 guard 只是限定策略适用域；需要全 15 点测量才能检查未知测试点是否一起命中。
- 没有实际性能数据时，源码可逆、host 不变、模型正确都不能表述成“保证其他点不退化”。
- 接受用户明确的退化反馈，不用缺少重复样本把退化一律解释为 Judge 波动。

## 9. 证据使用规则与容易混淆的地方

1. **版本身份分层。** 用户明确标注/更正的版本优先；按上下文关联的截图保留该限制。本地 source SHA 只能固定交付文件，不代表已核验平台编译文件。
2. **性能和诊断基线分开。** R25 Case5 约 6.5 μs，D24 基于 R23 时 Case5 回到约 7 μs，不能据此宣布 R25 成果丢失。
3. **0.00% 是界面显示。** 它是舍入后的指标，不等于真实误差为零，更不等于硬件输出逐位一致。
4. **阴性需要有效的阳性对照。** 对原本单组的路线再次压单组可能毫无变化；不能直接据此排除路线。Case7 新 R7 组与旧 C 旁路的解释必须区分。
5. **强响应只解码所测谓词。** “B==1”压力命中说明该条件，不说明精确 M/N；“S≥8”不等于 S==8；优化无收益本身不解码 shape。
6. **不拼接最低时延。** 每个截图的 15 项一起保留，不跨轮取各点最小值生成不存在的综合版本，不用非目标点平均变化比例校正目标点。
7. **平台最优列独立保存。** 它会随平台更新，不能作为同一提交的另一组输出，也不是已证明的硬件下限。Case15 的 4.05 μs 不能据此推出某个特定 kernel 架构。
8. **区分“未证实收益”与“确认失败”。** R14 的小幅变化、R15–R19 的缺失单独结果，与 R07 TLE、R20 编译失败、R30/R31 退化不是同一种状态。
