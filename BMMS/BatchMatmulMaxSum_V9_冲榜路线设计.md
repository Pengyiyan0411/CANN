# BatchMatmulMaxSum V9 冲榜路线设计

> 实现进度（2026-09-26）：已按用户授权落地原生 D128/D64、NT 小输出 S，以及组合候选；见 [实现状态](V9_impl/IMPLEMENTATION_STATUS.md) 和 [提交说明](BMMS_V9_SubmitPack/README_提交顺序.md)。D 首版为单层 K stage，尚未完成下文 K1/K0 两级复用设计。496 次源提取 CPU 模型检查通过，完整数值域仍有已知反例；没有 CANN 编译、NPU 验证或新成绩。下文保留原设计时点。

日期：2026-09-26。阶段：离线审计与设计；没有编译新内核，没有运行 NPU，没有产生新的比赛成绩。

**判断：应该换主攻路线。最值得投入的是按计算形态选择不同执行方式，并重新建立能够解释收益的实验；不宜继续把主要精力放在 C01 的 pM/pN 调参上。** 这并不证明 CATLASS 或任一新实现必然登顶。下文给出当前证据下优先级最高、可被实验推翻的 V9 方案。

## 1. 为什么值得换，而且不能只修一个点

| 证据 | 可以得出的判断 | 不能得出的判断 |
|---|---|---|
| P01 固定历史 T 复算 34.0599；C01 33.1428 | C01 没有证明调度代理模型能转化为性能收益 | 不能把未改分支的小幅波动全部归因于 C01 |
| 点 8–11 从 V4.3 至今长期接近原耗时 | 现有迭代未触及部分主要差距 | 不能只凭耗时断定隐藏 shape、布局或瓶颈 |
| 点 15：V7 29.38 μs，P01 110.22 μs | 自己的旧方案中有值得追溯的机制 | 不能直接按点号恢复 V7，也不能认定就是 Skinny |
| 当前 Native 只覆盖 K32/64/128、M/N 16 对齐的部分域 | 大 K、尾块仍需要新的执行主干 | 把已有 Native 的 K 模板改大不是完整方案 |
| `SmallOutput_LargeK` 已分类但无专属执行 | 存在结构性并行度缺口，值得独立路线 | 不能宣称它对应点 15 |

复算还揭示了投入优先级：**即使只把点 15 恢复到 V7 的 29.38 μs，其他点不动，总分也只是约 34.8362**。恢复历史优势有诊断价值，但不足以独自解决排名差距。假设所有点均比 P01 快 20%，冻结同一 T 后才约 42.9839；这只是评分算术，不是 V9 的成绩预测。计算记录见 [score_scenarios.json](V9_design/score_scenarios.json)。

点 12、14 这类相对 T 较近的点也要保护。评分取各点非线性得分均值，不按节省的总微秒加权；不能为了一个绝对耗时大的点任意牺牲其余点。真实 T 会变化，当前没有领先选手完整源码，也不能把逐点 T 当成一份可实现程序。

已装载 AscendC 开发编排、设计、性能优化、用例设计，以及 CATLASS 设计和性能优化技能，并阅读相关设计模板、归约/tiling/内存/流水参考。具体路径及适配记录见 [skill_application.md](V9_design/skill_application.md)。

本题已有固定 `run_kernel` ABI、单文件提交与现有单次启动约束，不能照技能模板新建一个 PyTorch/ACLNN 工程替代提交。用户明确要求无算力时先分析设计，因此本次不执行技能里的环境安装、编译、精度上机和性能测量阶段。

技能是设计检查框架，不是硬件事实的替代品。特别是：Cube 的 FP16/BF16 乘法配 FP32 累加仍保留；Vector 路径才按需要 Cast 到 FP32。512 B 对齐作为性能考虑，不能擅自排除合法尾块。缓冲区按实际数量重新算，不能照抄通用示例。

## 3. V9 的三条计算路径与一条保底路径

| 路径 | 目标输入族 | 核心改变 | 优先级 |
|---|---|---|---|
| D：完整 K 的 dense 流水 | 有足够 B/M/N 并行度、当前旧 Fast/Safe 域；优先 K≥256 | AIC 独立完成完整点积，AIV 经有界 GM ring 持续消费 row-max；移除应用层逐 stripe/逐基本块的 SDK 同步交接 | 主线 |
| S：确定性 Split-K | 小 B、小 M/N、大 K，空间任务数明显少于核组数 | 多核计算同一小 C 的不同 K 段，固定顺序逐元素合并 C 后才 Max/Sum | 与 D 并行准备，首轮重点对照 |
| V：Dot/Resident/GEMV | M=1、N=1、很小矩阵；四布局区别处理 | 保留已有效路径，专门比较长 K 的 Vector 与小输出 Cube；减少不必要固定开销 | 第二阶段，有实测再替换 |
| F：P01 保底 | 新路径尚未验证、精度/兼容性不满足的域 | 原 P01 路由及实现作为可回退对照 | 全程保留 |

例如 `(B,M,N,K)=(1,8,8,8192)` 合法，却不属于当前 Tiny/Resident/Skinny/Native，旧通用 tiling 的最小 M/N tile 为 16，最终只有一个 Cube worker。这是 S 路线的明确目标，不需要猜隐藏测试点。

生产版本只能按公开 shape、dtype、布局和设备核数选择路径。测试程序可以强制选路以便同输入比较，但不把隐藏点编号、输入数值、测评状态或运行次数用作路由条件。

初版路由顺序：先保留 Dot/Tiny/Resident 及现有 GEMV；其次检查经过验证的 S 域；再次检查经过验证的 D 域；其余原样进入 P01。新域不会因为“理论更先进”自动接管。最终阈值在同输入设备证据之后确定。

## 4. D 路线：选择 CATLASS 的矩阵乘构件，不直接套融合样例

详细接口、组件、资源表、伪代码和同步契约见 [design_bmms9_catlass_dense.md](V9_design/design_bmms9_catlass_dense.md)。

官方源码已固定到 CATLASS v1.4.0，commit `bcb3e52b6be3004b28996fb48af65ce48710c8f4`。首个对照选择 `MmadAtlasA2Pingpong` 的全 K GEMM 构件，自定义外层 ring 调度及 row-max epilogue。它是便于验证的起点，不是预先认定最快的最终版本。

这次源码检查约束了几个容易写错的设计承诺：

- 此版本 Pingpong 要求 L1 与 L0 的 M/N tile 相同；它的 L1、L0A/B 有双缓冲，L0C 是单缓冲。不能直接宣称四种粒度任意解耦、双 L0C 全部现成。
- 官方普通 `MatmulEpilogue` 使用完整 C workspace；本题需要自定义有界 ring，不能换个 epilogue 名字就得到融合方案。
- 官方 reverse flag 不是“两个消费者都已读完 ring”的信用。FREE 必须绑定真实的读完成，READY 必须绑定真实的写完成。
- 官方 Atlas A2 XFAI 同样使用 GM 中转。V9 不承诺 A2 上 C 从 L0C 直接送 UB，也不承诺消灭全部 C 搬运。[官方 XFAI 设计](https://catlass.readthedocs.io/zh-cn/latest/2_Design/04_contrib/00_XAttention/03_xfai_kernel/)

D 的第一收益假说是**让目前仍走旧通用路径的输入获得明确的 AIC/AIV 并行生产消费**。P01 本来就有 small-K Native、在线 Max 和双槽，因此这些概念本身不是创新点。若同形状测试显示旧主干已足够快，而新构件重读输入或单 L0C 排空更慢，则否定该具体候选，不强行推广。

全 K 累加与复用必须做真实取舍。若让 128×256 的 C 宏块全 K 驻留，FP32 C 就占 128 KiB，不能再免费拥有同样大小的第二槽；若改为 64×128 微块全 K，则下一个输出微块通常会重新搬运输入 K 段。V9 初版承认这种重读，先测清楚；第二轮才比较更大输出块、输入驻留或 `MmadAtlasA2PreloadAsync`。环形槽变小只是降低峰值 workspace，不自动减少 C 总写读量。

## 5. S 路线：用更多核算小输出，但不提前 Max

初始候选范围是 `M,N>1、max(M,N)≤64、M×N≤2048、K≥1024` 且空间任务数少于可用核组。此范围只是测试范围，不是已批准上线的最佳阈值。Split 数候选为 `1/2/4/8/16`，受有效 K 分块数和可用核数限制；K 段边界按输入元素/指令要求对齐，最后一段带真实长度。

数据流：

1. AIC 各自完成一段 K 的 FP32 C_partial，写各自独占的 `[batch, split, Mp, Np]`。
2. 对应 AIV 在 Cube 写完成之后确认该 partial 可见；所有参与 AIV 在合法的统一 barrier 会合。
3. 指定合并 AIV 按固定 split 顺序逐元素 Add 或固定树合并整个 C。必要时采用补偿累加，补偿方式同样需验精度。
4. 所有 K 段合并完，屏蔽 N padding 为负无穷，再逐行 Max，最后对 M Sum。

`workspace = 4×B×S×Mp×Np`，另加实际需要的对齐/同步区。S 是按每 batch 分配的 K 段数；任务数大于物理组时必须静态循环处理且全部任务结束再会合，不得用等待尚未调度核的自旋 barrier。

以 B1/M8/N8/K8192、S8、Mp=Np=16 为例，partial C 只有 8 KiB；理论上把长 K 工作分给 8 个组，但实际加速受小矩阵 Cube 利用率、输入搬运、合并和同步成本限制。必须与单核 Cube 和 Vector 点积版本一起比较。不得用原子加法改变跨运行数值顺序；不得对每段 K 先取 Max 后合并。

## 6. V 路线与 V7 历史优势应怎样处理

本次逐函数复核发现，V7 与 P01 的 Dot、Tiny、Resident、Skinny 等主体保留一致；P01 顶层 Tree 已覆盖其相应退化布局的全部合法 K。不能继续沿用下层旧注释，误称长 K `[K,L]` 一定回到 Cube。

V7 的 Panel 才是被舍弃的重要机制：本地 AIC Matmul、明确的 panel stride、双槽，以及消费者读完即释放信用。但 V7 在点 8/11/12 明显更慢，因此只作为本地对照，不能整体回滚。它的 `ASCENDC_CUBE_ONLY` 宏也不能直接放进 P01 的全局 MIX 编译单元；移植应采用明确的低阶 Cube 主体或证明局部编译模式兼容。

M=1、N=1 保持逐条完整点积后再归约。N=1 时虽然实数代数上可以交换求和次序，但这会改变中间舍入，题面也约束计算顺序；不将它作为默认“算法降阶捷径”。近似搜索、采样 N、假定输入非负/归一化、降为 FP16 C、把最大值当可提前判断，都不进入主线。

## 7. 精度是独立门槛，不能从数据流推导通过

完整 K 后 Max、跨 N 保存逐行最大值、最后 Sum，是数学语义约束；并不证明 FP32 实现对所有有限输入满足 FP64 golden 的误差要求。

本次有一个可构造的 FP16 反例：M8192/N16/K32，各 B 列只有 `k0=1,k1=2^-13`；A 的行交替为 `[1,2^-12,0…]` 与 `[-1,0,…]`。FP64 整体 golden 为 `2^-13`；每个点积先转 FP32 后得到交替的 `1,-1`，最终为 0，误差约 `1.2207e-4`。即使最后 Sum 精确也无法恢复已丢失低位。

因此，“FP32 Cube + FP32 C + 补偿最终 Sum”不能被标记为全输入域精度证明。这个缺口现在就已成立，**裸 D0 只能作为吞吐/集成诊断对照，不应单独进入可提交路由**。V9 必须同时保留官方结果和独立完整 FP64 oracle，记录严格双门槛与历史组合容差；不因历史 15/15 Pass 就隐去对抗例失败。只按 shape 保底也不能自动解决同 shape 内的消减反例。

数值路线单独设计为 Q：比较“有可靠误差区间的快速计算，不能认证时高精度重算”与“从 dot 开始保留 hi/lo”。两者都必须覆盖 dot、Max 和最终 Sum，且都尚未完成实现或证明；不能只加强最终 Sum，也不能拿裸 D0 的耗时代表含 Q 的正式版本。具体决策与退出条件见 [precision_route.md](V9_design/precision_route.md)。

若要对整个题面字面域给严格保证，还存在有限 BF16 输入可产生超 FP32 范围输出的问题；有限输入与有限输出不是同一个条件。当前不猜评测数据的隐含界限，也不把输出截断来伪造正确性。此类规范问题与实际冲榜性能分开记录，见 [precision_architecture.md](V9_design/precision_architecture.md)。

大边界 golden 应按 batch/M/N 分块，每一小块仍完成完整 K 的 FP64 点积，保存 FP64 行最大值，全部 M 求和后才转 FP32。直接分配完整 FP64 C 在合法输入上可达几十 GiB；用例清单生成不能等同于张量全部物化。

## 8. 卡时有限时，实验怎样安排

**现在不用申请卡。先完成实现和离线检查，再用一次有退出条件的短实验选择路线。** 本次已准备参数清单，未实现 V9 kernel 或完整设备 runner；不把它称为即传即跑的测评包。

卡时启用前完成：单文件交付和依赖闭包、源文件 SHA、固定 P01 对照、分流记录、分块 golden、用例及输出路径、失败退出、预算退出。若能在无卡 CANN 编译环境完成编译就先做；没有时将编译耗时计入首轮预算。

首轮建议软预算 20 分钟、硬上限 30 分钟；它是将来 runner 的停止策略，不是承诺能在此时长内编译成功，更不代表现在已启动计费。

| 顺序 | 内容 | 决定什么 | 退出规则 |
|---|---|---|---|
| 0 | 记录 CANN/SoC/核数/编译参数，验证单文件能编译 | 基础兼容性 | 首次编译失败只允许一次明确修复；反复失败回离线 |
| 1 | 32 个 smoke、强消减反例、重复运行、输入未改检查 | 含数值处理的新路径能否进入性能候选 | 精度/有限性/死锁任一失败，停止该提交候选的性能验收 |
| 2 | 16 个代表输入，P01 对 D/S；同输入 GEMM-only 诊断仅按需加 | 是否真的改对执行主体 | 新旧无可分辨差异，不扩大参数搜索 |
| 3 | 仅选 2–3 个确有问题的输入采详细时间线/流水指标 | Cube、Vector、搬运或等待谁限制性能 | 达预算即导出结果并退出 |
| 后续独立轮次 | 胜出分支四布局/双 dtype 的完整精度和同集性能 | 扩覆盖、确定公开条件分流 | 通过后才考虑正式提交 |

裸 D0/S0 如用于独立的吞吐研究，必须标成诊断内核，只在相应输出通过检查的普通输入上比较执行主体；这种实验不属于提交候选的精度/性能通过记录。强消减反例不必等上机后才承认其数学限制。

同一实验冻结形状、输入、参数与源 SHA。热身后做交错 A/B/B/A，至少两个独立进程轮次；输出中位数、分位数与各轮原始记录。小于观测波动的差异不算胜出。详细 profiler 可能扰动微秒级内核，轻量 Task Duration 与详细诊断分开采。规则所需的最终比较使用相同计时口径；Host 分配/同步时间另记，不能与 device 时间混算。

不做无证据的大网格 autotune。每轮只改变一个问题：第 1 轮主干/并行方式；第 2 轮输出 tile 或 L1 K 深度；第 3 轮才考虑交接批量、N 分片或输入驻留。三轮没有解释清楚收益就回设计，不靠不断提交碰运气。
