## 结论

**以你指定的 R14 作为后续分析和开发起点。按这次截图的 T 复算，R14 为 37.259712 分，直接父版 R11 为 36.937232 分，差值 +0.322480。** 当前没有重复测量，不能把这个差值解释为确定的优化收益，但也不必因此停下开发。[I14][H14][P]

**第 11 点的大突破主要是 R11 已有的收益：R11 为 100.71 μs，R14 为 100.56 μs，只再下降约 0.15%。** 不能把 R10 约 135 μs 到 R14 约 100 μs 全部归功于 R14 的“少开核”。R14 对父版的净增分约 78.68% 来自第 1、9 点，而不是第 11 点。[H11][H14]

本轮新增的结构判断有三项：

1. **R14 的新增调度范围比名字看起来更窄。** 它仍只处理 R11 已经满核单波次的形状，因此 `B` 不能整除可用核数的场景仍不会进入这层优化。
2. **纯网格优化应开始按上限止损。** 本轮抽取实际 host 规划器执行 20,087 组设计样例；R14 只在其中 57 组进一步改变 R11。这个样例集合不是隐藏测试分布，但能说明它是局部补丁，不是全新的计算路线。
3. **下一轮先验证“快路径覆盖缺口”，然后投入“少搬 A＋缩短输出生命周期”。** 仓库已经有 R15/R16 覆盖候选，不能把它们重新包装成新想法。前沿方案中，保序压缩仍可研究，但必须先解决“候选元素很少、候选微块却几乎全覆盖”的问题。

## 3. R14 的真实技术路线

### 3.1 版本关系

```text
R08：继承大 K 宏块流水，小 K 改四微块成包
 └─ R10：在原计划恰好满核单波次时，重排宏块网格
      ├─ R12：独立修改末段 N 合并，不属于 R14
      └─ R11：把部分短第二波改成满核单波次
           ├─ R13：仅尝试剩余多波次使用略少核的单波次
           └─ R14：仅尝试已有满核单波次使用略少核的更均衡网格
```

R14 不包含 R06 的整宏块 MMAD，不包含 R12，也不包含 R13 的新增范围。[C14][README][H11]

### 3.2 大 K 核的计算和存储仍是原结构

| 层次 | R14 当前实现 |
|---|---|
| L1 计算宏块 | 128×256，K1=256 |
| L0 微块计算 | 64×128，K0=64；一个 K0 切片最多四次 MMAD |
| L1 输入 | A/B 分别双缓冲，合计显式分配 384 KiB |
| L0A / L0B | 显式分配 32 / 64 KiB |
| L0C | 四微块合计一份 128 KiB 宏块输出，不是双宏块输出 |
| GM ring | 两个宏块槽，256 KiB/核组 |
| Cube/Vector | 每个 AIC 配两个 AIV；两个 AIV 各处理部分行 |
| AIV 输入 | 一份 16 KiB 消费输入 buffer，逐微块搬入 |
| 最终归约 | `[B][pN][M]` 行最大值 partial，N 分片 Max 合并后一次 Sum(M) |

数值来自附件显式分配公式，不是任意型号的资源上限声明。精确位置见 R14 第 2529–2535、2714–2797、2808–2896 行。[C14]

**目前的融合没有保存完整 C，但并没有消除所有 C 的 GM 中转。** 宏块核仍通过 `Fixpipe<float,float>` 写 ring，再由两个 AIV 读入 UB；每个有效 C 元素仍参与这次写和读。GM 地址的访问可能被缓存服务，逻辑流量不等于实际 HBM 事务量。[C14]

### 3.3 R14 新增的 host 决策

其逻辑可以压缩为：

```text
先得到 R11 的计划
    │
    ├─ 不是 tasks==cores 且 blocks==cores → 原样返回
    │
    └─ 枚举 75%～不到100%核数的单波次矩形网格
          宏块数、有效 C 元素数、输入长度三个峰值
          都至少降低12.5%，才考虑替换
```

候选核数满足：

\[
\lceil 0.75C\rceil\le Bp_Mp_N<C,
\qquad \text{tasks}=\text{blocks}=Bp_Mp_N.
\]

这里的 C 表示可用核组数，不是结果矩阵。12.5% 是代码的结构门槛，不是测评噪声阈值，也不是设备提速承诺。[C14]

具体例子：合成 `B=1,M=3072,N=768,K=256,C=20`，R11 的 20×1 网格最忙组做 6 个宏块；R14 选择 6×3 网格，只启动 18 个核组，最忙组做 4 个宏块。**少开两组反而减少最慢组工作量**，因此这个设计是有结构依据的。

但这不代表其端到端一定提升 1.5 倍：全局 A/B/C 总工作并未随峰值下降，减少核数可能减少聚合带宽，pN 增大还会增加 partial 与最终 Max 合并。

## 4. 本轮实际做的 CPU 规划审计

### 4.1 检查方法和范围

从本轮 R14 附件抽取 `bmms11r2` 的 host 规划函数，补最小类型定义后，用 `g++ -std=c++17 -O2` 编译运行。独立按任务和宏块循环计算各核组工作量，与源码的闭式峰值对照。

设计集合为：

```text
cores = 8,16,20,24,32,40,64
B     = 1,2,3,4,5,7,8,16,32,64
M     = 128,144,256,512,768,1008,1024,1536,2048,3072,4096,8192
N     = 256,272,512,768,1008,1024,1536,2048,3072,4096,8192
K     = 256,512,4096
```

先筛除不满足附件宏块 `Eligible` 的组合。检查的是规划器，不是完整 dispatcher，也不是设备核数值模拟。

| 实际检查结果 | 数量 |
|---|---:|
| 合法设计组合 | 20,087 |
| R11 相比 R10 改变计划 | 738 |
| R14 相比 R11 再改变计划 | 57 |
| R14 仍有每组多任务的组合 | 10,133 |
| R14 峰值宏块数等于全核宏块计数下界 | 11,042 |
| 覆盖、总量、峰值、候选门槛断言失败 | 0 |

相同 B/M/N/cores 在不同 K 下可能重复同一个计划，故不能把这些比例当作输入分布上的概率。多任务也不自动等于低效：任务足够且均衡时，多个任务本来就合理。

**本检查没有验证 NPU 的舍入、MTE 可见性、READY/FREE、编译器生成代码或设备耗时。** 辅助包包含抽取器、实际检查源、输出和哈希。

### 4.2 三个值得注意的限制

**限制一：R14 仍然间接要求 B 整除可用核数。**

`tasks=B*pM*pN`，而进入新增层必须 `tasks==cores`。因此，虽然新计划可以少开核，入口却仍然要求原来的 B 能整除 cores。`B=3,cores=20` 不会被这一层修复。[C14]

**限制二：R14 优化的是独立峰值，不是经设备标定的总时延。**

`peak.input` 是输入长度单位；给定同一 K，乘上 `2K` 才是 16-bit 输入的逻辑字节量。代码没有把 K、转置布局、Cube 发射、Fixpipe、Vector、partial 合并和实际带宽统一成实测时延模型。它是轻量结构启发式，不能当作普适最优规划器。

**限制三：到达计数下界后，再修网格不会消除主流水成本。**

设总宏块数为：

\[
Q=B\left\lceil\frac M{128}\right\rceil\left\lceil\frac N{256}\right\rceil.
\]

在“完整宏块不再拆分、把每个宏块视作同等工作”的模型内：

\[
P_{\min}=\left\lceil\frac QC\right\rceil
\]

是最忙组宏块计数下界。若当前峰值为 P，进一步均衡可减少的计数比例至多为：

\[
h_{\mathrm{balance}}=1-\frac{P_{\min}}P.
\]

这是**宏块计数上限**，不是考虑尾块、带宽、流水的时延上限。它适合排除明显没有多少“块数均衡空间”的形状，不适合证明所有调度优化都无用。

### 4.3 用具体形状说明哪些还能挖、哪些应转向

以下全部是本轮 CPU 合成样例，K=256，20 个可用核组；不是对隐藏测试 shape 的推测。

| B/M/N | R14 任务/核组 | R14 pM×pN | 最忙组宏块数 | 全核计数下界 | 判断 |
|---|---:|---:|---:|---:|---|
| 1/1024/1024 | 20/20 | 5×4 | 2 | 2 | R11 已做到计数下界 |
| 1/3072/768 | 18/18 | 6×3 | 4 | 4 | R14 的少核策略有结构收益 |
| 1/4096/4096 | 20/20 | 5×4 | 28 | 26 | 块数再均衡最多减少约7.14% |

## 5. 当前真正尚未降低的成本

### 5.1 同样多的乘法和中间输出，被更均衡地分给了各组

本轮独立计数确认：在这些宏块计划之间，全局有效乘法对应的输出元素总数、宏块总数、输入逻辑读取总量不变。R14 改的是峰值分布，不是算法复杂度。

宏块对齐/带正确尾块处理时，输入逻辑读取量为：

\[
D_{AB}=2BK\left(M\left\lceil N/256\right\rceil+N\left\lceil M/128\right\rceil\right).
\]

C 的 ring 写读有效字节约为：

\[
D_C=8BMN.
\]

行最大值 partial 的有效写读约为：

\[
D_{\mathrm{partial}}=8Bp_NM.
\]

这些式子描述源码的有效数据工作量，未计缓存、事务对齐、ND/NZ 实际搬运和队列元数据，不能直接当作 HBM 带宽计数。

**R14 的 `peak.input` 下降不意味着上式 D_AB 下降。** 这正是下一阶段需要从“分得更均匀”转向“实际少搬一些”的理由。

### 5.2 A 的跨 N 复用仍然没有做满

`Process` 的 N 循环每次调用 `Macro`；`Macro` 都从 `LoadStage` 开始重新加载 A 和 B。即使相邻 N 宏块对应同一个 M 宏块，A 仍然重新进入加载流程。[C14]

而小 K 专用核已经有 A 阶段驻留，因此这一建议特指大 K 宏块核，不能作为对小 K 的“新优化”。

### 5.3 输出依赖仍有明确的串行环

```text
MMAD 完成 → Fixpipe 读完 L0C → L0C 可被下一个宏块覆盖

Fixpipe 写好 GM 槽 → 两个 AIV 均读完 → GM 槽可被覆盖
```

这是两个不同的资源生命周期。扩大 GM ring 或增加包长，只改变第二个环的容量，不能自动解除第一个环的 `FIX_M` 依赖。[C14]

消费者也没有因为“成包”而一次预取全部结果。宏块 AIV 仍使用单 buffer，逐微块清填、搬入、等待、Max、释放。是否处于关键路径，需要单变量实验或 profiler，不应只凭存在 fence 就认定它一定是主瓶颈。

## 6. 下一轮：先做三个有明确归因的实验

**首轮不要继续单纯把 75% 改成 70%、把12.5%改成10%，也不要把四条改动合成一份盲测。** 以 R14 冻结文件为当前主线，下一轮优先使用下面三个互不叠加的实验。

### 实验 A：补 K 为32对齐、但不是固定小K的覆盖缺口

现有原生小 K 只覆盖 32/64/128，大 K 两条手写主线要求 K≥256 且32对齐。这使 K=96/160/192/224 可能落入旧回退体系。[C14]

仓库已经有 `R15_K32_GAPS`，正是这项实验；不是本文新发明。它以 R11 为父版，只改 guard，复用现有分块生产者，保留 Tiny/Resident 和原生小 K。[HK]

两种干净做法：先按归档用 R11 控制验证已有 R15；或把它的**相同窄范围 guard 修改**重新施加到 R14，并重新检查。不要直接用 R15 文件覆盖 R14 后，还把差异称作“只改 K 覆盖”；已有 R15 不含 R14 网格层。

采用依据是目标域正确且出现能复核的收益，不能仅根据 case 序号选择代码。没有隐藏 shape，就无法提前承诺第 8 点一定命中。

### 实验 B：补 K%32==16 的覆盖缺口

仓库已有独立 `R16_K16_TAILS`，接管 K=48..8176 且 K%32==16 的部分对齐形状；同样以 R11 为父版，不能直接视为 R14 累积后代。[HK]

这会让现有分块流水首次遇到16元素的 K 尾部。归档记录了 CPU 地址、guard 和故障注入检查，但未提供目标 NPU 的通过结果，所以仍需平台验证。

**不要顺手把所有 K%8==0 都放进去。** 当末尾只剩8个元素，源码里以 `kr/16` 为循环次数的 LoadData 可能漏掉数据，需要显式零填到16，并分清原始 GM stride 与补齐后的片上 stride。这已不是“改 guard”级别的变化。

同理，M/N 非16对齐不能直接松开 guard：当前分块加载、`vr=mr/2` 分行和尾部 DMA 都依赖现有对齐条件。它应当是独立尾块核，而非顺手扩大范围。

### 实验 C：大 K 路径的 A_RESIDENT，先限制 K=256/512

**目标：同一个 M 宏块扫描多个 N 宏块时，完整 A 只搬入一次。** 保持既有四微块 MMAD、K0 累加顺序、GM 协议与消费者，尽量只改变 A 的生命周期。

在 ar=128、输入16-bit、B仍按两份 K1=256 面板缓存时：

| 配置 | A 的 L1 显式分配 | B 的 L1 显式分配 | 合计 |
|---|---:|---:|---:|
| 当前 | 128 KiB | 256 KiB | 384 KiB |
| A完整驻留，K256 | 64 KiB | 256 KiB | 320 KiB |
| A完整驻留，K512 | 128 KiB | 256 KiB | 384 KiB |

因此在这两个限定 K 上，可以在不超过当前 L1 显式分配规模的前提下尝试。但不是简单把 `LoadStage` 移到外层：

- TA=true 时，A 的 NZ 地址计算要使用完整 K 的布局步长，而不是某个 K1 小面板长度。
- TA=false 时，K 偏移必须包含 `kBase+kk`，不能重复读取第一面板。
- A 的“可覆盖”事件改为整个对应 N 扫描结束才释放；B 的面板事件仍独立维护。
- 只在一个组确实扫描多个 N 宏块时启用；只有一个 N 宏块就没有跨 N 重用收益。

对于一个任务内 n 个 N 宏块，A 的逻辑读取由 n×ar×K×2 降为 ar×K×2；B 和 C 的该项流量不变。

但收益上限也应算清楚：忽略尾块，当前每个 C 元素对应输入逻辑读取约 `3K/128` bytes，C ring 写读为8 bytes。K256时，A是总计14 bytes中的2 bytes；K512时，A是20 bytes中的4 bytes。即使完全消去这一部分，简化纯带宽模型的加速上限也只是约1.167×和1.25×，实际还受缓存和其他阶段限制。

**这不是一个“保证翻倍”的想法，但它确实在减少真实的源码数据工作量，而不只是继续重新分工。**

## 7. 更大的工程突破：非对称生命周期，而非统一放大 tile

### 7.1 文献给出的启发

FlashAttention-4 从不同硬件单元不均衡的速度出发重排流水；其调度也考虑局部性，而不仅是任务数量。Asymmetric Tile Buffering 则研究输入驻留尺度与输出尺度分离，并把切换成本纳入分析。前者目标是 Blackwell，后者实验平台是 AMD XDNA2；都不是 A2 参数表。[S1][S2]

对本题值得借鉴的是：

> A 可以驻留很久，输出 C 却应尽早完成、搬出并释放；这两者没有必要绑定成相同大小、相同寿命的宏块。

### 7.2 具体候选：K256 的 64×256 双 L0C 输出

当前 128×256 宏块占一份128 KiB L0C。可独立探索：两个64×256的输出，各64 KiB，形成真正的输出乒乓。

限定 K256 时，完整 A128×256 占64 KiB，两个完整 B256×256 面板占256 KiB，L1总计320 KiB，仍在当前显式分配范围内。

一个半宏块完成完整 K 后就交给 Fixpipe；另一个半宏块使用另一份 L0C 计算。关键不是“少开几个 fence”，而是给两个依赖环真正不同的物理存储。

**不可隐藏的代价：** 在保持当前有限 L0B 容量的实现中，先算完上半 M 再算下半 M，可能让同一 B 从 L1→L0B 重载两次；当前结构则能在一个 K0 切片内让两个 M 微块共用 B。GM 输入不增加，不代表所有片上搬运不增加。这项设计必须同时衡量释放 L0C 的收益和 L0B 重读的代价。

K512不能直接照搬上述“双完整 B 面板”分配：A128 KiB＋双B512 KiB共640 KiB，超过当前384 KiB显式分配规模。需要重新规划，不能把K256实验无条件扩大到K512。

### 7.3 AIV 预取也应做成真正重叠，而不是只改队列深度

宏块消费者当前一份16 KiB输入 buffer。增加第二份后，在当前 Max 进行时搬入下一微块；只有所需 READY 已到达、目标 UB 槽可用时才能发起预取。

按附件宏块消费者显式分配式，M=8192时原申请合计131744 bytes；加一个16 KiB输入槽后为148128 bytes。此为显式数据buffer合计，未包含框架/事件等开销；是否可用仍以实际SDK资源分配为准。

注意当前代码已经在最后一次 MTE2 读取完成后发 FREE，而非等全部 Vector 运算结束；不要把这项已有的早释放再算成新贡献。新的预取必须保持两个 AIV 都完成对应 GM 读取后，生产者才能复用整包。[C14]

“满块不清填”可作为预取前的窄范围实验：只有 DMA 确实覆盖全部有效 vr×TN 时才能省掉初始化；N尾部的 −∞ 仍必须正确。旧 R05 同时改过部分清填与归约策略且未确认稳定收益，因此不能保证这一处独立改动一定提速。

## 8. 调度线保留，但用上限决定是否值得做

Stream-K 的核心是从固定 tile 分配转向工作量分配，以缓解网格量化导致的闲置；论文不是本题 MaxSum 的实现。[S3]

对仍有大缺口的形状，可以继续推进此前提出的完整 K `FLAT_ROW_STREAM`：按行展开宏块，每个组拿一段连续区间，只在跨组的行段边界保存额外的行最大值，最终按 M 原顺序求和。

与直接 Stream-K 不同，先不拆 K，因为：

\[
\max_n(x_n+y_n)\ne\max_n x_n+\max_n y_n.
\]

切 K 后若未先合成完整 C 就做 Max，会改变语义；先合成 C 又可能重新引入大量 partial C 和数值顺序变化。

建议先采用计数缺口明显的域，例如 `P/ceil(Q/C)` 较大的形状；保护 R14 已经接近下界的域。这个比例是筛选线索，不是固定12.5%那样的性能承诺。最终还要考虑 A 连续扫描复用、跨组行段数量和 partial 成本。

因此我的判断不是“调度已经没有空间”，而是：**R10/R11解决的那类大尾波问题有价值；继续在已经均衡的同一矩形网格里细调，优先级应下降。**

## 9. 对上一轮高风险想法的一个关键补充：候选少，不等于重算少

保序量化筛选的数学依据仍成立：对同一行有限 FP32 点积，确定且单调不减的映射 Q 满足：

\[
Q(\max_j c_j)=\max_jQ(c_j).
\]

保留最高量化桶中的所有元素，会包含原 FP32 最大值的索引。但必须区分“保留原FP32最大值索引”和“最终满足FP64 golden”；后者还要求重算顺序、点积误差及候选误差界正确。溢出和全桶碰撞也需要完整回退。

官方 Fixpipe 的 A2 V220 接口列出 FP32 到 FP16/BF16 的 GM 搬出能力，可作为低位宽 C 通信的实现基础；这不证明当前安装版本、具体舍入模式和整个恢复方案已经通过。[S4]

本轮进一步算出一个很容易忽略的代价。假设：

- 一个重算微块覆盖64行；
- N=2048，列微块宽128，共16个N微块；
- 每行只有1个候选；
- 各行候选落点独立且在16个N微块中均匀分布。

若必须按原64×128微块重放，触及N微块数的期望为：

\[
16\left[1-\left(\frac{15}{16}\right)^{64}\right]
\approx15.7428.
\]

即约 **98.39% 的列微块仍要重算**。这是显式假设下的概率模型，不是对你的实际输入分布的测量。它说明即使“每行只剩一个候选”，也可能几乎重算全部 Cube 微块。

因此这条路线的第一指标不应再只是候选数，而应是：

```text
候选对数量 / 原始点积数量
实际重放微块数量 / 原始微块数量
候选重算的输入读取量
完整筛选＋恢复时延
```

能否把候选 `(m,n)` 对打包成高效率且精度达标的点积任务，才是这条高风险路线的真正难题。没有解决前，不应把它放到三个近期提交实验之前。

## 10. 执行与验收：少量实验，但每个都能回答一个问题

| 顺序 | 实验 | 只回答的问题 | 不应同时改动 |
|---|---|---|---|
| 1 | 窄域 K32-gaps 覆盖 | 某些合法 K 是否被旧回退限制？ | 核组网格、精度、输出协议 |
| 2 | 窄域 K16-tail 覆盖 | 现有分块流水能否高效接管16元素尾K？ | M/N尾块、量化、归约顺序 |
| 3 | K256/512 的 A 驻留 | 跨 N 重复搬 A 是否值得消除？ | MMAD宏块形状、C通信精度 |
| 后续分支 | 半宏块双L0C / AIV预取 | L0C/UB生命周期是否限制流水？ | 不与新调度一起首次提交 |
| 有明确计数缺口时 | 连续行段调度 | 非整除、多任务尾波是否能改善？ | 不在已接近下界域硬切换 |

已有 R15/R16 可以先用对应 R11 控制完成实验，不必重写；其有效改动再迁移到 R14。若直接在 R14 派生，应分别命名为明确的 R14 后代，绑定哈希并重新做 guard/地址检查。本文没有替你执行迁移或把新代码冒充已通过版本。

性能比较使用 `R14 → 候选 → R14` 或已有实验配套的同父版控制。每次固定 T 重算，保留全部15点；一个候选没有明显变化时，先核实目标域是否命中，不把无变化自动解释为“这条算法无效”。没有shape日志时，不通过故意失败猜隐藏点。

正确性优先保留完整 K 后 Max、Max 后 Sum、负数尾部 −∞、四种布局、输入不修改、重复输出一致。已有3项极端数值限制在归档中仍未修复，不能把15/15 Pass扩展成对整个数学输入域的证明。[P][H14]

**最终优先级：R14冻结 → 快路径覆盖验证 → A驻留 → 输出生命周期重构。调度只继续攻明显未解决的尾波域，保序压缩作为独立研究分支。**
