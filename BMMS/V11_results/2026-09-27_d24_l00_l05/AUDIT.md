## 源码条件与几何结论

L05在实际Split-K路由通过资格检查后，对原始plan判断：

```cpp
B * p.mTiles * p.nTiles == 1
// p.mTiles = ceil(M / 64), p.nTiles = ceil(N / 128)
```

这三个量都是正整数，乘积为1意味着B=1、mTiles=1、nTiles=1。
结合该路由的16对齐及K资格，Case15当前可确定：

```text
B = 1
M ∈ {16,32,48,64}
N ∈ {16,32,48,64,80,96,112,128}
4096 ≤ K ≤ 8192，K % 32 = 0
原空间任务数 = 1
```

L01_B_EQ1、L02_M_LE64、L03_N_LE128三个条件已经被L05联合确认，可以跳过。
它们是“未提交但逻辑已解出”，不是伪记为已跑Pass；进度单独记录于[PROGRESS.json](PROGRESS.json)。
K区间既符合此前C系列线索，也由本次实际进入Split-K的资格条件直接支持。

## 旧R03与当前Split-K的并行区别

将上述几何代回R03 planner，pM=pN=1、tasks=blocks=1。
这从源码解释了此前Case15的P02单组压力探针为什么没有明显响应：原R03本来已是单任务。

当前R23正常plan的空间任务数仍为1，但launch blocks等于K分片数S，S≥2。
因此不能将L05阳性解释成“正常R23仍只用一组”。L00/L05命中后的plan才是splits=blocks=1。

原S仍未知。由源码：

```text
S = 不超过 min(16, cores, floor(K/512)) 的最大2次幂
S ∈ {2,4,8,16}
```

L05没有给出精确M/N/K、TA/TB、FP16/BF16或M×N≤4096。
M≤64、N≤128仍允许M×N达到8192，不能直接认定SmallOutput_LargeK。
