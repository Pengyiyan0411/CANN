# 首次 NPU 验证：r03 与 r06

2026-09-28。结论：环境与编译/验证闭环已经打通；r03 保持主线。r06 通过本轮正确性验证，但一个命中其守卫的合成大矩阵没有明显性能收益，因此不晋升。

- CANNLab，Ubuntu 20.04.5 / aarch64，CANN 9.0.0，驱动25.5.5，bisheng clang15.0.5。
- PyTorch 可枚举两个 Ascend910_9362 逻辑设备，本次串行使用 device0。
- ACL 查询 cube core count=20；日志中的目标样本 grid=5×4、blockDim=20。
- 远端目录：`/home/developer/bmms_v12_lab_20260928`。
- 编译沿用已提供的 Judge CMake 链接库与 `--npu-arch=dav-2201`；使用与原 main.asc 一致的 TensorInfo/TensorGroupInfo ABI。
- 测试 launcher 是新建的独立离线 harness，隐藏15点不可用。因此不能宣称复制了比赛私有计时器或完整输入分布。

## 正确性

| 版本 | 冒烟 | 完整合成集合 | 每组重复 | r06守卫命中用例 |
|---|---:|---:|---:|---:|
| r03 | 8/8 | 34/34 | 3 | 18（仍执行原R06） |
| r06 | 8/8 | 34/34 | 3 | 18（执行新宏块路线） |

集合包含：

- B1/M8/N8/K64 的小输出路线；B4/M32/N32/K128 的 Native 路线。
- B1/M1024/N2048/K1024 的完整宏块和 B1/M1040/N2064/K1056 的双向尾块。
- 上述常规形状均覆盖 FP16/BF16 与四种 TA/TB；另有零值和全负矩阵输出。
- 参考结果由实际量化后的输入在 CPU 上进行独立 FP64 matmul、行max及行sum计算，分行块生成。
- 每次调用前将输出写为不同 NaN 哨兵，全部输出要求有限且满足 `abs(error)<=1e-4+1e-4*abs(reference)`。
- 两版最大误差/容差比均约0.001394。这里只说明该集合通过，没有声称所有支持 shape 或隐藏15点通过。

`results/*_manifest.jsonl` 的 host_call_mean_us 包含函数内 planner/分配/同步/释放；不能与 Judge 的 kernel 微秒直接比较。

## 第一轮性能 A/B/B/A

固定合成输入 B=1、M=1024、N=2048、K=1024、FP16、NN。它不是已知的隐藏 Case9 精确形状。

使用 `msprof --task-time=on --ai-core=off`，每个进程调用40次，丢弃前10次后汇总30个 kernel Task Duration。采集顺序：r03_a → r06_a → r06_b → r03_b。

| 轮次 | r03中位数/μs | r06中位数/μs |
|---|---:|---:|
| a | 35.01 | 34.91 |
| b | 34.80 | 35.84 |

CSV 确认 r03 运行 `bmms11r2_f16_nn`，r06 运行 `bmms1206_f16_nn`，不存在未命中优化分支的问题。

结论：没有观察到稳定的明显改善，不进入更大规模精测或晋升。本轮仅两个独立进程对照组，没有给出统计显著性承诺；30个连续调用也没有当作30个独立实验。当前数据来自轻量 profiler，而非无profiler正式比赛复验。

## 流水计数器诊断

另开两轮 `--ai-core=on --aic-metrics=PipeUtilization`，同样丢弃前10次；与前表分开解读。下表是工具导出的字段中位数，不能相加为总时间，也不能直接视作关键路径时间。

| 字段/μs | r03 | r06 |
|---|---:|---:|
| Task Duration | 36.14 | 37.10 |
| aicore_time | 27.9035 | 28.7930 |
| aic_mac_time | 16.0420 | 16.0350 |
| aic_scalar_time | 22.1010 | 17.4710 |
| aic_mte1_time | 12.1265 | 12.0055 |
| aic_mte2_time | 14.4675 | 14.7180 |
| aic_fixpipe_time | 4.1635 | 4.1700 |
| aiv_time | 33.8310 | 34.7835 |
| aiv_vec_time | 3.5460 | 3.5460 |
| aiv_scalar_time | 10.1735 | 10.9065 |

r06 减少指令调度的目标确实有响应：aic_scalar_time 下降约21%；计算量未变，MAC时间几乎不变。整体时长未下降，不能从“MMAD指令4→1”推导大幅加速。

AIV总时长与Vector忙碌时间差距较大，为同步、标量工作、等待和尾部收敛提供检查线索，但不能仅凭这两个数断言consumer就是瓶颈。下一步应结合时间线观察 AIC/AIV 生产消费重叠、ring等待及末尾归约；若另一个shape簇呈不同特征，独立选择策略。

## 去留与下一步

1. r03 仍为已接受 SOTA，未更换任何提交源码。
2. r06 现在有真实设备编译和34例正确性证据；性能只获得上述单个合成shape的否定性筛选结果。
3. 暂停围绕“继续增大MMAD就会显著加速”的盲扫；先观察执行时间线，或转向 Native 13/14 与 Split-K 15 的代表簇进行独立profile。
4. 34例不是完整跨route回归。后续晋升仍需长K、padded、skinny等保留路线及比赛15点验证。
5. 未改驱动、CANN、PyTorch或设备电源策略，未运行多个NPU任务争用同卡。
