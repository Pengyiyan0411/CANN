## 需求与证据边界

优先尝试前四个小点，尤其Case1短点积。历史工作画像：Case1为B=M=N=1、K32..128；Case2为B1、M/N2..16的Tiny/Resident；Case3/4为对应多batch。隐藏精确shape、dtype、布局和Case3/4实际路由尚未独立确认。以下所有加速数据都是同卡合成输入的配对比较，不能冒充隐藏Case1–4成绩。

运算始终为FP32点积，然后按N取最大值、按M求和；没有使用半精度乘积、近似数学、输入数值路由、缓存答案或跨调用状态。

## 排查与实现

1. Case1已经是一核、一次launch、K常量化，没有跨核归约。CANN9实际头文件显示通用ReduceSum在短归约收尾时有V→S数据交接；先验证是否值得替换。
2. Case2的r03已经批量计算乘积，但Tiny仍逐点积调用ReduceSum。原多batch Tiny/Resident还有较多逐行工作和同步。批量归约的预期收益明显大于再改一遍batch循环。
3. 为把所有点积一次归约到稠密的行数据，r69把N向上补齐到8。这样可让每行起点满足32字节对齐，但增加了乘积数量。这是必须通过独立留出评估的代价。

采用Ascend C性能优化技能，工程保持现有单ASC/ACL ABI。该工程没有ascend-kernel Python扩展脚手架；沿用已经验证的C ABI/msprof方法，CPU FP64只作精度参考，本机r41是性能标杆。code-gen技能缺失，API细节以实际安装的CANN9头文件及官方文档核对。

| 版本 | 改动 | 初步结论 |
|---|---|---|
| r68 | 短点积显式WholeReduceSum；K>64为两个部分和加法 | K≤64约3%–5%，更长K无稳定收益；不提交 |
| r69 | 常量K、batch独立归属、多个点积一起归约；保留Tiny/Resident原有K归约分组 | 多batch收益明确；B1且N需补齐的Resident有退化，不能无条件采用 |
| r70 | 短点积TBuf单次执行、显式事件、DMA补零后一次Cast | 26组耗时下降中位1.71%，绝对约0.018μs；不提交 |
| r71 | 只收窄r69主机路由，不修改其设备代码 | 1204配置/3668调用精度通过，168组新性能中位下降7.75%；仪器化发现索引尾部告警，不交付此版 |
| r72 | 修正索引向量存储/初始化，并恢复向量mask | 完整版本精度/配对性能通过；新模块重点仪器化检查清零，建议Judge15 |

以上是三个算法实验及一次路由收窄集成。r71保留r41短点积，不合并无明确收益的r68/r70。

| 新形状留出，全体 | 320 | 10.54% | 28 |

| 留出B17 | 80 | 11.02% | 0 |

多batch留出的240组全部改善，最小约2.0%。B1退化集中在Resident且N补齐的形状；例如15×9×112补齐为15×16×128的乘积存储/处理范围，较r03增加了N方向工作。最差退化10.95%，故拒绝完整r69。

r71接管范围：

```text
1 <= B <= 64
2 <= M,N <= 16
32 <= K <= 128，K % 8 == 0
满足原Tiny或Resident门槛
并且 B>1，或者原Tiny，或者N%8==0
```

其余范围执行r41。Case5的16×16×128不满足原Resident门槛，不会被新路由接管。新路径分配核数为min(B,2*availableCoreNum)，没有硬编码核数；一个核处理一个或多个完整batch，无GM中间结果和跨核求和。

## 验证方法

- FP16/BF16先量化输入，再用CPU FP64计算参考；误差门槛`1e-4+1e-4*abs(reference)`。每次调用前用NaN覆盖输出，并检查全部batch。
- 第一批860配置：13种短K、四种转置布局、B1/4/17/32/41/64、奇数M/N、负值、零、尺度变化、相同列、K抵消与行抵消。基线、r68、r69、r70各通过860配置×3次调用。
- 额外8配置覆盖最大静态UB形状M16/N9/K112、B41、两dtype四布局，r69已通过每配置10次。
- 静态枚举2726个合法M/N/K组合，核对索引边界、32B对齐、repeat≤255及UB尺寸。最大显式分配167968字节，低于当前卡192KiB UB；这只是布局检查，不替代NPU测试。
- 性能使用轻量msprof task-time，严格串行A/B/B/A，每个版本两个独立进程窗口。点积每配置100次丢20次；小矩阵80次丢20次。统计逐窗口中位数后比较，保留所有原始样本和实际kernel名。
- 新路由冻结后另生成336组不同形状/种子，168组用于最终性能验证；不能把此前用于选择路由的320组再称为最终独立留出。

点积本机task-time约1μs；本轮两种简化没有显示足够稳定的绝对收益。这不证明硬件下界，也不证明Case1没有别的优化方向，只说明不能据此承诺Judge中2.xμs会明显下降。

## API核对

归约步长、repeat上限按实际SDK以及[WholeReduceSum官方说明](https://www.hiascend.com/doc_center/source/en/canncommercial/800/apiref/ascendcopapi/atlasascendc_api_07_0081.html)核对；dstRepStride以输出元素计，srcRepStride以32字节块计。r69在248处拆分，保证第二段目标地址仍为32字节对齐。

显式补零按[DataCopyPad官方说明](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/SIMD-API/basic_api/memory_vector_compute/data_move/DataCopyPad_GMToUB.md)核对，并由实际CANN9编译与精度测试验证；r70只补至下一16个半精度元素，不读取未初始化尾区。

## 仪器化检查发现与修正

第一次工具运行因输出目录权限被拒绝，工具仍返回0；没有生成精度JSON，因此未认定为通过。改为独立0750目录后真实执行。

全34配置全核memcheck速度较慢，在完成13配置后主动中止，没有冒称完整覆盖。已完成部分中，旧R52的K72在Mul附近出现越界报告；它属于未修改的原路径，尚未定位，不能断言是误报，也不能称整个提交所有旧路径已经sanitizer认证。

随后对新路径单独做6配置、B2全核的mem/race/init/sync，以及B41重复使用缓冲的block0检查。r69/r71的新代码确实仍有告警：K32 Gather索引区与相邻packed区潜在WAR；K56/K112索引尾部未初始化；K112索引缩放处越界。数值通过不能抵消这些证据，因此暂缓交付r71。

r72将索引pitch单独设为`IP=ceil(K/64)*64`，不再复用乘积的kp；先初始化完整索引区为0，再生成有效K个索引，并按IP缩放。尾部索引保持0，避免读取未初始化索引或紧邻的packed区。最后恢复mask。运算顺序、核心归约策略、r71路由和其他路径不变。

为缩短仪器化编译时间，新路径单独提取为模块构建；提取的模块与完整r72代码逐字节一致，记录独立SHA256。完整r72仍独立编译并做全部精度与性能复验。新路径模块通过也不能替代整个历史代码的全路由sanitizer验收。

## 决策与下一步

1. **优先验证Case3/4**：多batch同类输入收益最稳定，来自减少逐点积/逐行处理，而不是单纯增加核数。精确隐藏路由仍须通过实际成绩确认。
2. **Case2保守接管**：保留Tiny及N已对齐的Resident，补齐成本较高的B1输入回退；不能把多batch收益直接外推给所有单batch。
3. **Case1暂不更换**：两种实现均未达到预设收益门槛。下一步若继续攻点1，应先独立核对旧点积K72告警和实际K/计时范围，不能仅凭“短点积”预期大幅下降。

提交r72全15点，重点反馈1–4；5–15也保留回归检查，尤其已取得明显收益的8/11/15。Judge反馈前，MAINLINE的accepted_sota仍是r41，active_candidate标记r72。
