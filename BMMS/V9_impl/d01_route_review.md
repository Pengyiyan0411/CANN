## 2. D01 中已能确认的结构性代价

源码依据：`V9_impl/dense_fragment.asc` 的 `LoadStage`、`LoadL0`、`Emit`、`Process`，以及复用的 `bmms83::SmallKConsumer`。

| 机制 | 源码事实 | 性能含义和证据边界 |
|---|---|---|
| C 基本块较小 | TM64×TN128，每块完整 K | 相较更大 C 块，会产生更多输出任务和重复输入搬运；具体旧 SDK tile 未知 |
| 每个 C 块重读 A/B | `Emit` 从 k0=0 重新调用 LoadStage | AM256/BN512 仅规定消息顺序，没有恢复旧 small-K 的宏块输入驻留 |
| K 粒度未分层 | L1 K 与 L0 K 同为128 | 每128 K均发一组 GM→L1 和 L1→L0 操作；无法独立优化 GM 搬运深度和 MMAD K |
| single L0C | 下一输出块先等上一 Fixpipe 的 FIX_M | 相邻输出块的 MMAD 与前一块 Fixpipe 缺乏独立 C 缓冲；GM 两槽不能替代双 L0C |
| 块末排空 | 每个输出块末清空两套 L1/L0 event，然后写 C | 有利于 correctness，但会破坏跨输出块的更长流水；不得把它称为无缝 persistent GEMM |
| AIV 工作与最终会合 | rowmax、partial、SyncAll、最终 Sum | 这些仍有固定成本；仅看 Cube 主体不能预言融合总时间 |
| 最小占用分片 | pM 优先，不足时 pN 补核数 | 避免明显静态闲核，但不是已验证的性能最优调度，仍有尾片/任务波次影响 |

上述事实支持“D01 是正确性优先的第一条全 K 主干，尚非高吞吐最终主干”。它们不能确定哪一个是点12的主瓶颈。尤其不能只依据 294.81 μs 就宣布是 HBM 带宽、bank conflict 或特定 K 值。

## 3. 为什么先做 D02，而不是立即重写 M/N 复用

已直接对比打包文件 `D01_DENSE_K128.asc` 与 `D02_DENSE_K64.asc`：除了首行标签，唯一源码差异是 `BMMS9D_K_BLOCK 128 → 64`。D02 已经准备好，信息来源较干净。

| 比较项 | D01→D02 |
|---|---|
| 接管条件、Plan、M/N 分片 | 不变 |
| TM/TN、consumer、GM 两槽、single L0C | 不变 |
| 全 K 数学工作量 | 不变；但累加指令分组不同，仍须重新验证精度 |
| 对齐主体逻辑 A/B 总读取字节 | 不变；真实 cache/HBM 行为仍可能不同 |
| C 的写读总量、rowmax工作量 | 不变 |
| K 迭代、MMAD 和部分 event 次数 | 约翻倍，尾段有离散差异 |
| L1/L0A/L0B 显式有效空间 | 减半；L0B由满64 KiB变为32 KiB |

**可证伪假设 H1：D01 的坏表现明显依赖 K128 的搬运/MMAD 形态。**

- 支持它的结果：D02 在 D01 大幅回退的点显著恢复，并且恢复超过可见复测波动。此时不能进一步单凭结果断言“L0B容量是原因”，只能确认这组 K 形态值得用。
- 反对它的结果：D02 的回退形态几乎不变或更差。此时停止 K=32/48/96 的无方向扩展，转向跨输出块复用/流水。
- 混合结果：按完整15点比较，不选择最大单点倍数；为有实测支持的公开输入族保留不同实现。没有 shape/route 证据时，不按点号写规则。

如果本轮只再提交一份，选 **D02**。若可多一份，再用 **P00_CONTROL_P01** 做同平台新鲜对照；它用于排除环境漂移，不产生新的性能路线。

## 4. D02 之后的新实现应回答什么

### 4.1 若 D02 明显恢复：优先拆开 K1/K0

候选为 L1 K1=256、L0 K0=64，TM64/TN128不变，consumer/Plan/ring保持不变。L1 A+B 两槽 192 KiB；L0A/B 两槽分别16/32 KiB；single L0C32 KiB。它保留 D02 的 MMAD K 形态，同时摊薄 GM→L1 的提交次数。

**H2：K64 的 MMAD 有优势，但 K64 的每段 GM 搬运/事件过密抵消部分收益。** 对比同输入 D02；若 K1=256 后没有改善，不能继续将“更深 L1”作为既定正确方向。

K1/K0 分层**不是 M/N 方向输入复用**。完整输出块所读 A/B 总字节仍相同，不应以“输入流量减半”描述这个实验。

### 4.2 若 K64 不能解释回退：低改动成本的双 L0C 检验

可基于 D01 或两者中较有希望的一版，只将 L0C 改成两个32 KiB槽，并将 `FIX_M` 复用等待改为对应 C 槽再次使用之前。Plan、K stage、C tile、输入读取方式及 consumer保持不变。

**H3：相邻输出块被 single-L0C 的 Fixpipe→MMAD 依赖显著限制。** 双 C 总计64 KiB，静态容量允许，且原 P01 small-K Native 有可参考的双 C 生命周期。若这一步几乎无变化，就不能继续把 single-L0C 当作主要解释。

这个实验仍不自动恢复整个跨块流水：当前输入事件在每输出块末排空的开销依旧存在。不得把预计改善写成保证，更不能绕过两消费者 FREE 协议。

### 4.3 高吞吐主干最终应有真正的 M/N 输入复用

完整对齐的大问题中，忽略 cache 和分片边界，当前逻辑输入读取量约为：

`2*B*K*(M*ceil(N/128) + N*ceil(M/64))` 字节。

在足够大的整齐矩阵上，A/B 两项比例约为 1:2。因此：

| 复用目标 | 理想逻辑输入流量相对当前 | 需要什么 |
|---|---:|---|
| 同一 M64 下，两相邻 N128 共用 A | 约5/6 | 在完整 K 内保留两块 C、复用 A 的 L1/L0数据 |
| 相邻两 M64 共用相同 B | 约2/3 | 在完整 K 内保留两块 C、复用 B；调整消费顺序或消息组织 |
| 2×2 个64×128块共用 A/B | 约1/2 | 四块C共128 KiB，接近L0C全部容量；重新设计事件和consumer遍历 |

这些只是**特定整齐大形状下的逻辑流量比例，不是用时预测**。小 M/N、尾块、N分片、cache驻留和任务并行度会改变实际效果。

有两个重要实现限制：

1. 不改变现有 consumer 时，同一 M tile 的相邻 N tile是连续消息；优先做 N方向两块配对，协议改动较小。它只能减少 A 重读，收益上限不如同时复用 A/B。
2. 两 M tile配对会改变现有 AM→BN→mo→no 消息顺序。例如先得到 `(m0,n0)` 和 `(m64,n0)`，旧 consumer接下来却可能在等 `(m0,n128)`；**不能只把 AM 或 TM 改大就提交**。必须让 producer与consumer共同采用新的明确次序，并保存跨 N 的逐行状态。

仅将 C 基本块扩到128×256虽然可降低重复，但一份FP32 C就占128 KiB，不能同时要求两个同样大的 L0C槽。宏块、微块、输入复用和 C 双缓冲之间是真实取舍，不是可全部叠加的免费选项。固定官方 CATLASS优化文档也将输入搬运、负载均衡与 tile选择作为需实测的取舍：[本地固定版优化指引](../V9_design/references/catlass/docs/contents/advanced/catlass_optimize_guidance.md)。

## 5. 路线与实验优先级

| 优先级 | 动作 | 是否需新代码 | 目的 |
|---:|---|---|---|
| 0 | 保持 P01 保底，不把 D01 广泛推广 | 否 | 避免已知总分回退成为新基线 |
| 1 | 提交现成 D02；条件允许补 P00 新鲜对照 | 否 | 用最小变量得到 K 形态敏感性证据 |
| 2A | D02明显恢复时，设计 K1=256/K0=64 | 是 | 拆开 GM 深度与 MMAD K形态 |
| 2B | D02无解释力时，先做双 L0C 单变量 | 是 | 排查相邻 C 的 FIX/M依赖；不是大网格调参 |
| 3 | 开发真正的 M/N复用主干 | 是 | 减少当前每输出微块重读输入的结构性成本 |
| 4 | 根据公开输入族的设备证据收窄/组合路由 | 是 | 保留真实优势域，旧SDK继续处理更擅长的域 |
