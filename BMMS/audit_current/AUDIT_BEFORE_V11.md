## 2. 题目要求与审计口径

依据 [cann.md](cann.md)，每个 batch 独立计算：

\[
y_b=\sum_{m=0}^{M-1}\max_{0\le n<N}\sum_{k=0}^{K-1}X_{1,bmk}X_{2,bkn}.
\]

| 约束 | 当前验收要求 |
|---|---|
| 逻辑与归约 | 完整 K 点积后 Max(N)，再 Sum(M)；不跨 batch 配对 |
| 输入 | 同 dtype 的 FP16/BF16，连续 ND；允许负数 |
| 存储布局 | X1 为 `[B,M,K]` 或 `[B,K,M]`；X2 为 `[B,K,N]` 或 `[B,N,K]`，四种组合均须支持 |
| 合法维度 | `1≤B≤64`，`1≤M,N≤8192`，`32≤K≤8192` 且 `K%8=0` |
| 规模 | `B*M*K≤2^26`、`B*N*K≤2^26` |
| 输出 | FP32 `[B]`，不得出现 NaN/Inf；不得修改输入 |
| 边界 | 全负行不能以 0 初始化最大值；必须处理 M/N 尾块；重复执行应一致 |
| golden | 输入实际存储值参与完整 FP64 计算，最终 y 转 FP32 |
| 计分 | 15 点全部通过后，各点分数等权平均 |

题面 FP32 误差文字是相对、绝对误差各 `<1e-4`。存档模板 `original/scripts/verify_result.py:61` 使用 `np.isclose(rtol=1e-4, atol=1e-4, equal_nan=True)`，它属于组合容差，不等价于两个独立门槛；也不能据此推断线上 Judge 的全部行为。当前应分别记录独立绝对误差、独立相对误差、组合容差、有限性与重复一致性，不能把输入 dtype 为 FP16/BF16 自动解释为输出放宽至 `1e-3`。

存档 `BatchMatmulMaxSum.py:81` 附近虽注释“15 个测试用例”，实际列表仅含一个 K=4 的示例；题面示例也有 K=2。它们用于说明语义，不能作为合法边界集或隐藏 15 点 shape 清单。

本报告的证据分层：**源码/本次复算可确认的事实**、**既有文本记录或归档报告**、**仍待验证的推断**。15/15 的措辞均指所附文本记录，并非本次设备复测。

## 4. 最新实现的实际分支

依据 `P00_V8_3_1_BASELINE.asc:2481–2520` 的入口及继承 dispatcher：

1. 从合法元数据获取 B/M/N/K、dtype、布局和可用核数，并进行输入合同检查。
2. `M1_NContig / N1_MContig` 进入 Tree GEMV；这两类分别要求 M=1 或 N=1。
3. Native 要求 M、N 均至少 16 且均为 16 的倍数，K 为 32/64/128，排除 Tiny/Resident。Tile 为 64×128，自适应选择 pM/pN。
4. Native 在 `pN==1` 时保存补偿 hi/lo 标量 partial；`pN>1` 时保存逐行最大值并跨 N shard 合并，再沿 M 求和。
5. 其余进入 `bmms80d_dispatch`：Resident、连续 `[L,K]` Skinny、适用时的旧 lane-GEMV、small-K family planner，最后回退 V7.1/V4.3 通用路径。

**Tree 与 Native 的形状条件互斥。** 因而同一个固定输入对 P03 和 P02 都发生变动，不能直接解释为同时命中了这两个顶层分支；编译差异、运行条件与测量波动仍需排除。

本次静态核对的入口依赖合法元数据，没有发现按隐藏测试编号选择路径的逻辑。该结论限于所检查入口与探针改动，不构成对整个 CANN 工具链、缓存时序或全部设备执行的认证。

## 6. 重点审计发现

以下优先级是审计整改优先级；没有新增已实证的线上 kernel WA 结论。

### 高：运行结果与源码身份尚未闭环

位置：探针包 `P01执行结果.md:120` 最后一组标题仅为“执行结果”；`RESULTS_TEMPLATE.md:5–19` 是历史两列；`README_PROBES.txt:4` 将 P00 称为 known-good，但缺少本轮编号结果。

本次核对 9 份 `.asc` 的字节数和 SHA-256，均与 manifest 一致。然而结果文件没有提交号、实际上传文件哈希、编译配置、设备/核数、测量时间和重复样本。**磁盘源码身份可确认，结果属于该源码的绑定仍依赖人工记录。** 未编号组须补身份；P00 应与候选在同一轮条件下重测。

### 高：V8.0 数值脚本不能充当正确性验收门

位置：`BatchMatmulMaxSum_V8_0_implementation/test_lane_semantics.py:20–22, 41–43`。

两项确定问题：

1. 脚本只统计和打印最大绝对误差，没有容差、有限性或相对误差断言；正常退出不能解释成“精度验收通过”。
2. `ref` 先将每条 FP64 点积转换为 FP32，再以 FP32 求和。题目 golden 是 FP64 点积、Max、Sum 完成后才将最终 y 转 FP32。尤其 Sum 路径二者不等价。

本次构造合法 K=32、L=17 的 FP16 输入：`x[0]=1, x[1]=2^-12`，bank 的非零项为 `bank[0,0]=1, bank[0,1]=-1, bank[1,0]=2^-13`。现有脚本参考为 0，完整 FP64 golden 为 `2.9802322e-08`。这是参考语义差异的最小复现，不是设备失败证据。

脚本仅覆盖 K≤256、L≤1024 的随机数值，且以 Python 模型模拟 lane 算法；不能据此给 V8.3 Tree、Native 或全部合法范围作正确性背书。planner 脚本同样是独立 Python 实现，未直接执行提交源码中的规划器。

### 中：P05 不保证每个任务至少 4 个 tile

位置：`P05_NATIVE_MIN4_TILES.asc:2045–2047`；任务实际划分见 P00 `SmallKConsumer` 中 `mt0/mt1/nt0/nt1`。

过滤条件为 `ceil(mTiles/pM) * ceil(nTiles/pN) < 4` 时拒绝。这检查较大的分片尺寸，不是所有任务的最小尺寸；初始 `(pM,pN)=(1,1)` 候选也未经过该门。

本次依源码算式建立的 Host 模型给出合法反例：`B=1,M=448,N=128,K=128,cores=2`，P05 选择 `pM=2,pN=1`，两个任务分别为 **3 和 4 个 tile**。因此 P05 结果只能说明“这版启发式过滤未改善当前记录”，不能据此证明细粒度任务完全必要，或排除所有 oversplit 问题。此反例是 Host 模型复现，未运行 Bisheng。

### 中：P01、P04 的因果解释需要收窄

P01 除改写 partial workspace，还移除 scalarBuf、补偿 partial 累加和对应合并逻辑。它测试的是整套 epilogue 实现，不是某一条 scalar 指令。P01 保留的 NativeCost 仍含偏向 scalar partial 的 pN==1 成本项；未据新 row-max 流量重新校准。

Case 5 从历史 8.20 到 P01 7.19 μs，足以把 row-max 版本列为复核候选；不能据此推出所有小 M 均应使用某阈值，更不能认为删去补偿累加后整个合法域精度仍有保证。

P04 的 `maxPN=1` 不仅限制 N 并行，也可能重新选择 pM、改变任务波次和输入复用，并在原 pN>1 的情况下切换到 scalar epilogue。因此 Case 14 的 15.05→49.20 μs 强烈支持保留原策略，但不能将全部退化只归因于 N 并行度一个因素。

| 已排除普遍 oversplit | 只能说两种所测限制策略未显示收益，不能排除整个问题类别 |

旧分析给出的相关系数可复现：以历史 V8.3.1 为基线的**绝对耗时差向量**，P02 与末组为 `r=0.963831`，与 P06/P07 分别为 `0.008626 / 0.132558`。若改用相对变化，分别变成 `0.995946 / −0.246767 / −0.014457`。报告相关性必须注明口径；相关性不等价于实际 K、shape 或分支识别。

Case 8 所有探针耗时范围为 90.33–92.81 μs，Case 15 为 108.20–112.32 μs，确实缺少明显的单一路径响应。可据此优先设计有正确 fallback 的路径隔离实验，不能直接编写基于猜测 shape 的替代实现。

### 中：按绝对微秒差距安排比赛优先级会误导

旧分析的 8/9/10/11/15 占总 `t−T` 差距约 86% 可复算为 **85.9524%**，但题目不按总耗时评分。

以 P01 为起点，只让一个点缩短 10%，其他点不变，理论均分变化为：Case 12 **+1.0245**，Case 14 **+0.5134**，Case 1 **+0.2673**，Case 8 **+0.0706**，Case 15 **+0.0350**。这是评分公式的敏感性演示，不是这些改善必然可达的预测。

Case 15 若真能从 110 μs 级变到接近 9 μs，仍有很高价值；但小幅优化 Case 15 与大幅换算法是不同工程任务。合理优先级应结合可实现的加速幅度、全表得分增益、正确性风险和开发成本。
