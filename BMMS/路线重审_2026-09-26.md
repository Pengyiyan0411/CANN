# BatchMatmulMaxSum 路线重审

结论：应调整主攻方向与实验方法。保留 P01 作为暂定正确性/性能对照，停止继续围绕 C01 的 pM/pN 规则迭代；将主要精力转向通用密集计算的数据流、退化输入专用执行方式，以及 V7 优势路径丢失的原因。现有证据支持“当前优化重心不足以解决差距”，尚不能证明某个全新实现必然领先。

本次按用户最新要求暂缓 P01/C01 专项上卡。先前测试包仍保留，但不再作为下一阶段主任务；当前不需要因此启动或购买环境。

## 1. 支持换方向的证据

8–11 的主要差距长期没有收窄；15 还丢失了自己的历史优势。靠修改 K128 的分片规则，不能预期自动改善尚未定位的其他输入族。

P01 约 34.0599 分，C01 约 33.1428 分，均沿用此前记录的 T，后者截图不含当前 T。早期报告采用过不同 T：例如 V4.3 的 31.1967 分不能直接与当前同列比较；用当前 T 重算为约 30.1826。分数比较应冻结同一组 T。

当前没有领先选手完整提交与源码，逐点 T 也未证明来自同一份提交。因此不能推断对手一定采用某种算法，或把每点最优拼成可实现的一份领先程序。

## 2. 对现有路线的修正认识

### 已经做到的事

当前代码已有分块 Max、局部 row-max 累积、有界 C 缓冲、部分纯 Vector 专用路径，以及 K32/64/128 的低阶 Cube producer。把“采用融合、双缓冲或在线 Max”重新命名为新路线，没有实质意义。

### 仍然限制主线的结构

- 通用 Safe 的 `ComputeTile` 先 `IterateAll<true>` 完成一个 stripe，再从 GM 读取并归约；函数级代码没有把下一 stripe 的生产与当前 stripe 的消费显式重叠。不能由此断言 SDK 内部所有指令串行，但可确认应用层交接粗粒度。
- 通用 Fast 使用同步 `Iterate/GetTensorC` 消费基本块、执行行归约，并受 `FlatFastStream` 的顺序安全门限制。是否命中该门、SDK 内部重叠是否充分，需要真实数据。
- 新 Native 的覆盖范围仅为 K32/64/128 且 M/N 对齐并通过分流条件的子域；任意 K、尾块和其他形状仍大量依赖旧通用实现。
- C01 改变空间分片，但没有改变这些路径的核心执行组织。活跃核数、tile 工作量、逻辑读取字节等代理指标不能替代真实性能分解。

我之前优先推进 C01，缺少“调度是当前主要瓶颈”的设备证据，优先级应调整。CPU 模型验证仍有价值，但它主要约束正确性，不能用于认定下一优化的收益。

## 3. 应换成的主攻路线

### A. 重建高吞吐密集核心

将以下四种粒度分开设计：核间任务范围、L1 输入复用区间、L0 矩阵乘块、Cube/Vector 交接块。K 可完整驻留时复用输入；K 较大时显式沿 K 分阶段搬运并完成 FP32 累加；只在对应点积完成后做 N 维 Max。

目标是扩展当前 Native 未覆盖、旧通用路径仍占主导的合法域，并检验流水是否真正重叠、归约是否反向阻塞 Cube。保持四布局、BF16/FP16、尾块和严格精度要求，不能只以一个对齐 FP16 shape 的结果代表整类。

可参考 CATLASS Atlas A2 XFAI 的 QK 计算段和分层存储/流水组织，为本题重写 Max/Sum epilogue。其官方设计明确包含 GM 中转，因此不承诺照搬 CUDA 的“中间结果零 GM”路线；具体接口必须匹配目标 CANN 版本。

参考：[CATLASS XFAI Kernel 设计](https://catlass.readthedocs.io/zh-cn/latest/2_Design/04_contrib/00_XAttention/03_xfai_kernel/)。这是可参考的实现组织，不是已证明的本题领先方案。

### B. 单独解决小矩阵与退化输入

Dot、小矩阵、M=1、N=1 不应被迫承担完整密集 GEMM 的固定成本。按真实物理连续方向设计批量点积/向量归约，避免不必要的逐行控制和跨核汇合。但当前隐藏 Case 15 是否属于这类仍未确认。

本次核对 V7 与当前 P00：`SkinnyDevice`、`MakeSkinny`、`UseSkinny`、`UseResident` 函数体完全相同。该事实削弱了“Case 15 的退化一定源于旧 Skinny 实现本身”的解释，更应检查实际分流、V7 panel 的差异和编译/运行条件。相同函数体不能单独证明实际执行相同，也不能完全排除编译性能变化。

### C. 恢复能解释的历史优势

V7 的 Case 15 曾为 29.38 μs，是本项目自身已观察到的显著优势，应优先追溯其机制。不能直接把整个 V7 替回，因为其 8–12 点显著退化；也不能依隐藏点编号路由。找到对应合法 shape/layout 家族后，才能选择性恢复或移植机制。

## 4. 验证方式也要改变

后续在使用卡时之前先准备少量代表 shape 与完整 FP64 golden。一次设备实验同时测：同输入的矩阵乘对照、当前融合路径、新执行路径，以及必要的退化输入实现。

测量要回答具体问题：

- 矩阵乘本身是否已经远慢于可比实现？如果是，先改矩阵乘块、输入布局和复用。
- 融合路径相对其矩阵乘主体增加了多少成本？是否主要消耗在搬运、归约、事件等待和全局合并？
- 更换分片是否改变实际计算组、任务波次和 N 合并数量？

不同形状允许出现不同答案。与矩阵乘对照的比较用于诊断，不把诊断内核或拆分耗时冒充合法提交性能。

以“一种瓶颈假说、一组可比较内核、一次有预算的设备采集”组织实验。先得到可重复且能解释的局部收益，再扩大覆盖与提交；不再先堆许多启发式，然后靠 15 个标量耗时反推完整架构。

本次没有新写替代 kernel，没有执行 NPU 测试，也没有证明新的数据流达到某个分数。决策是终止当前局部调度主线，转入以上结构性路线的设计与验证。
